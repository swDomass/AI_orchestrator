# Architecture — Components

Detailed per-module reference. Linked from [CLAUDE.md](../../CLAUDE.md). Update both when behaviour changes.

**Execution flow**: Queue read → provider selection (fallback chain) → profile loading → policy check → skill gating → memory context injection → prompt building → provider execution → result persistence → heartbeat.

---

## `orchestrator.py`

Main loop (`run_once`/`run_watch`), prompt building (`_build_prompt` — task last under `## Aufgabe`, `PROMPT_TASK_DELIMITER` in front of it, and since 2026-10-05 `PROMPT_COMPLETION_RULE` under `## Systemregel` directly in front of the delimiter; since 2026-10-08 a prompt with no context above the task carries the rule too, only the delimiter is left out — `#tool:` tasks never reach `_build_prompt` on their run path, `tests/test_orchestrator_tool_tasks.py::test_a_tool_task_never_reaches_build_prompt`), file change tracking via before/after snapshots. `run_watch()` calls `_log_capacity()` once after startup delay so the dashboard timeline has a fresh data point from the first second. `run_watch()` starts `start_heartbeat_thread()` so scheduled checks fire during long tasks. Tool-task `error_code="timeout"` marks retry directly without provider fallback (prevents next provider failing non-retryably → `[-]` finalization that would incorrectly satisfy `#needs:` deps). `error_code="format_error"` (tool output broke its own format contract) shares the hang path: requeue with `HANG_RETRY_BACKOFF_SEC` under the persistent `<!-- hang: N -->` counter, blocked once `MAX_HANG_RETRIES` is exceeded, and no provider cooldown (a format break says nothing about provider health). Because the two share that counter it counts *fruitless attempts*, not hangs — two format errors plus a first genuine hang block at 3 — so the log/Telegram text names the joint count (`3. erfolgloser Versuch (Hang/Format-Fehler zusammen gezählt)`) instead of the old, false `zum 3. Mal`. A failed `#verify:` outcome check now flips the already-written ✅ to ❌ via `restamp_done_as_failed()` (`_restamp_after_failed_verify()`, paired with all three verify sites) — no retry budget needed, the line stays `[x]`. Before a task starts, `_worktree_gate_violation()` refuses to run a tool that declares `requires_clean_worktree` (only `dev-loop`) in a `cwd:` that is missing or not a clean git repo (a missing `cwd:` means the provider would inherit the orchestrator's own directory), and `parallel_runner._run_single_subtask()` applies the same check per subtask — terminal with `error_code="worktree_dirty"`, checked BEFORE provider selection so no token is spent, waivable per task with `#allow-dirty`, exempt for `#parallel` parents (see patterns.md → *Clean-worktree gate*). Every terminal-failure path now finalizes with `failed=True`, which stamps the queue line `- [x] <task> ❌ <ts> (<provider>)` instead of ✅ — out of the queue, but not a satisfied `#needs:` dependency (see patterns.md → *Terminal failure state*). `error_code="provider_not_allowed"` is terminal: a `#provider` tag barred by `tool_providers` is finalized with a clear message rather than parked for a quota reset that can never unblock it. `error_code="no_provider_allowed"` is the same verdict without a tag — when `dispatcher.policy_dead_end()` reports that the allow-list and the routable chain do not intersect (a typo'd provider name, or a profile whose provider order the policy excludes), the task is finalized too. Both paths exist because `select_provider() -> None` is ambiguous: it means "nothing allowed" (permanent) and "nothing available" (temporary, park and wait) alike, and only the second is worth a quota-reset wait. `_policy_dead_end_message()` (fixed 2026-09-04) takes the task and profile so it can name the cause instead of guessing one: `dispatcher.profile_dead_end_reason()` splits a profile-caused dead end into three buckets, because `_allows()` returns False for reasons that need different answers — **unregistered** (no CLI/API key here; policy.yaml cannot fix it), **uncapped-barred** (registered, but in `_UNCAPPED_PROVIDERS` with no allow-list resolved, i.e. the fail-closed default — the fix is an authorisation, not a correction), and **policy-barred** (an allow-list exists and omits it, the one case that really is policy). It returns `None` unless one of the first two applies, so a pure allow-list exclusion keeps the pre-existing message, which prints what the policy *does* allow. The predicate is `not any(p in _providers and _allows(p, allowed) for p in profile.providers)` and lives dispatcher-side because the raw `allowed` is gone by the time `_effective_allowed()` has run — a synthesised list is otherwise indistinguishable from a configured one. Its first version asked only "is NONE of them registered?", which reported the fail-closed case as a `tool_providers` policy problem, named a synthesised allow-list as if configured, and called registered providers unregistered. `run_once()` returns `None` when all tasks are blocked by `#needs:` deps — `run_watch()` then sleeps `SLEEP_POLL_INTERVAL` (5 min) instead of 30s busy-loop, and skips `notify_queue_complete()` to avoid Telegram spam. `error_code="auth_expired"` (Claude OAuth login expired, `providers/claude.py`; fixed 2026-09-16, extended Runde 2) reuses the `unreachable` cooldown shape (`provider.set_cooldown()`, default 30 min — a human `claude login` is needed, so a quota-reset wait or the generic 5-min retry is pointless) **on the two non-parallel run_once() paths** (single-shot and tool-task) and sends exactly one Telegram notice per outage via `_notify_auth_expired_once()`/`_clear_auth_expired_notice()` (dedup modelled on `limits._429_notified`). `_run_with_retry()` also bails out of its own in-run backoff for `auth_expired` (own bare-code check, deliberately NOT added to `TRANSIENT_ERRORS` — see providers/base.py), the same way it already does for the tuple's members: retrying a dead OAuth session locally within 10-40s is guaranteed to fail identically, so it costs one doomed CLI call and nothing else changes for `auth_error` (checked by its own test). Three sites that write the replay span (`_span.retry(...)` in the single-shot and tool-task `provider_is_forced` branches, and `_execute_tool_task()`'s retryable-outcome builder) previously fell back to writing an unclassified raw provider string — or the misleading literal `"rate_limit"` — straight into `error_code` whenever no bare code matched; all three now normalize through `providers.base.error_code_of()` with a taxonomy-known fallback (`provider_unreachable`/`tool_internal_error`). Measured before the fix: three raw `error_code` values in `logs/runs.jsonl` on 2026-09-09, one of them the literal OAuth message above. **The policy block is fail-closed since 2026-10-06:** its former `except ImportError: pass` / `except Exception: _log.warning("policy check failed")` fell through into execution (no approval, no DENY check); now one `except Exception` holds the task like the `timeout` branch — log + `append_log` + `notify_error` (each best effort), `_mark_retry_checked(+10 min)`, `_span.retry("approval_unavailable")` (`_span.error` if the requeue fails, the line then stays open), `return False`. Only the exact answer `approved` continues: anything else after the `denied`/`timeout`/`skipped` branches (`""`, `None`, an unknown word) raises `_UnusableApprovalAnswerError` into that same hold — `""` is reachable through the engine's one pending slot (`_respond()` releases its lock before `event.set()`, a second request in that window resets the answer). Tests: `tests/test_orchestrator_policy_fail_closed.py` (fault tests parametrised over five exception classes at three sites, so a narrowed `except` turns them red). **The hold's Telegram alert is throttled since 2026-10-08** (`_notify_policy_hold`): one alert per cause — exception class + text, never the task, so every task held for one fault shares it — and `config.POLICY_HOLD_NOTIFY_WINDOW_SEC` (6 h, at most 4 a day), `time.monotonic()`, a new cause at once. Decide, send, then record — and record only a delivered alert: `notifier.notify_error` returns `bool` since Korrekturrunde 1 (True only when `_send` reports delivery; `_send` swallows network errors, Telegram 5xx/429 and timeouts), so a send that raises or returns False is not recorded and is retried on the next hold, every 10 minutes as before the throttle (attempts, not a flood — none of them arrives); a fault in the bookkeeping alerts anyway. Remaining risk: a send that arrives but reports False repeats on every hold (as on master, every 10 minutes per held task) until one reports True. State `_POLICY_HOLD_NOTICES` is in-process (a restart alerts once more), main thread only, capped at 20 causes. Once every `check_task` of a task has returned (`classified = True`, before the verdict branches, which return early), `_notify_policy_recovered()` sends ONE all-clear and — only once `send_message` returned True — forgets the causes raised while classifying, so the next fault alerts at once (a lost all-clear is tried again by the next passing task; with `NOTIFY_ON_ERROR` off nothing is recorded, so no all-clear comes either); causes from the approval path get none (a passing `check_task` says nothing about it) and age out. Log, `append_log` and the requeue run on every hold. A broken `policy.yaml` reaches this hold since the same day (`check_task` raises `PolicyUnreadableError`).

**Runde 3 (2026-09-16), P1: `_execute_tool_task()`'s own retryable-vs-finalize decision defeated the whole fix for tool-tasks.** The seven multi-phase tools (`dev_loop`, `review_loop`, `research_qa`, `knowledge_transfer`, `security_audit`, `test_loop`, `brainstorm`) all compute `retryable=is_transient(provider_error)` generically for any provider failure inside their phases — and `is_transient("auth_expired")` is deliberately `False` (it needs a human `claude login`, not automatic retry). Left as-is, `_execute_tool_task()`'s `if tool_result.retryable:` gate (before the `else:` branch that finalizes with `failed=True`) took the wrong side for `auth_expired`: the task was finalized PERMANENTLY, and the outer loop's `if outcome.finalized: break` returned before the `auth_expired` cooldown/notify branch was ever reached — reproduced by review: `outcome.finalized=True`, no cooldown, no notice, task terminally failed, the opposite of the ANNAHME. Fixed by widening the gate to `tool_result.retryable or _tr_error_code == "auth_expired"` — the same "intercept the code before the finalization decision" shape `capacity_exhausted`/`tool_runtime_exceeded` already use, except those two arrive already `retryable=True` because the TOOL sets it explicitly (`_make_capacity_exhausted_result`, `dev_loop._terminal_runtime`), while `auth_expired` arrives generically through `is_transient()` and is therefore intercepted here once instead of in all seven tools.

**`#parallel` subtasks get the notice but NOT the cooldown, and the `#parallel` PARENT never retries/parks at all (known limitation, Runde 2/3).** `parallel_runner._run_single_subtask()` (both the plain and the tool-based branch) calls `_notify_auth_expired_once()` on an `auth_expired` result — same dedup helper, no second mechanism — but does not call `provider.set_cooldown()`. That is not a gap introduced by this fix: `_run_single_subtask()` sets NO cooldown for ANY error code today (not `rate_limit`, not `unreachable` either), unlike the two `run_once()` paths above. Checked in Runde 3 for an `auth_expired`-specific version of the P1 finalization trap above: there isn't one, because `run_once()`'s `#parallel` branch already finalizes the PARENT queue line unconditionally right after `run_parallel()` returns (`failed=not success_all`), for every error code, by design (#7 "the parent gets one aggregated result") — a subtask failing on `auth_expired` was already exactly as terminal as one failing on `rate_limit`, before and after the P1 fix. `_run_single_subtask()` never reads `outcome.finalized`/`.retryable` (only `.success`/`.error_code`/`.output`/`.output_tokens`), so the P1 override is invisible here either way. Closing either half (cooldown, or a per-subtask retry/park) means deciding how a cooldown set from inside one parallel worker thread should interact with sibling threads racing the same provider singleton, and/or whether a `#parallel` parent could ever be re-parked per-subtask instead of as one unit — out of scope here, named instead of silently worked around. See ROADMAP.md.

## `dispatcher.py`

Provider selection with fallback chain (**`_PRIORITY = ["claude", "codex"]`** since 2026-08-15), cooldown management, provider-bound model aliases: Claude (`#claude_haiku`, `#claude_sonnet`, `#claude_opus`), Codex (`#codex_5` → gpt-5.6-sol flagship, `#codex_5_4` → gpt-5.6-terra, `#codex_mini` → gpt-5.6-luna), Gemini (`#gemini_pro`, `#gemini_flash`, `#gemini_flash_lite` — still defined, no longer routed to), opencode (`#opencode_deepseek`, `#opencode_deepseek_long`, `#opencode_glm` — handpicked ZDR aliases only, see `providers/opencode.py`). Without a tag the CLI's own default model is used. `dispatcher._TAG_MAP` is the canonical list of every routing tag (29 entries: 23 model-specific aliases + 6 bare provider tags); `queue_manager.MODEL_TAG_RE` derives its alternation from it, so the two cannot drift apart — see `queue_manager.py`.

**Gemini left the chain (2026-08-15).** Reason: `IneligibleTierError` on the remaining path plus data-protection concerns about the HTTP mode. The withdrawal is layered, and all three layers matter — removing only one would leave a route open: out of `_PRIORITY` (no default routing), out of `policy.yaml`'s `tool_providers` (an explicit `#gemini*` tag is refused with `provider_not_allowed` rather than honoured), and `GEMINI_API_KEY` commented out in `.env` — which is what disarms the `_limits_ok()` short-circuit below that would otherwise report Gemini unconditionally available. `providers/gemini.py` and its aliases are retained; `get_provider_by_name("gemini")` still resolves, so tests and any future re-enable keep working.

**Policy-aware lookups for tool code.** `get_provider_by_name()` is the raw, **policy-blind** registry lookup and must not be used by tools: six of them resolved their cross-provider/second-opinion providers through it and thereby bypassed `tool_providers` entirely. All seven of those call sites now go through the helpers below. The last two (`tools/brainstorm.py`, `tools/scientific_investigation_phase2.py`) are the *resolution* step rather than the allocation step, and re-checking there is the point, not redundancy: an allocation list can be restored from a persisted state file or produced by the degraded fallback path, so it outlives the policy that made it. The one deliberate exception is `tools/critical_review.py`, which pairs `policy_allows_provider()` with the raw lookup so "policy said no" and "unknown provider" get different log lines. Tool code uses instead:

| Helper | Use |
|---|---|
| `policy_allows_provider(name, tool)` | predicate — lets a caller log *why* it rejected (policy vs. unknown name) |
| `get_provider_for_tool(name, tool)` | policy-filtered single lookup; None on unknown **or** barred. Delegates to `get_provider_by_name`, so a test that stubs that one still governs what tools can resolve |
| `policy_provider_lookup(tool)` | returns a `(name) -> provider \| None` callable — drop-in default for the `provider_lookup` parameter of the cross-provider allocation phases. Candidate tuples stay unchanged; a barred provider resolves to None and drops out of the loop |
| `forced_provider_policy_violation(task, tool_name=…, …)` | `(provider, allowed)` when a `#provider` tag is barred, else None. `select_provider()` returns None for both "policy said no" and "no capacity"; only the latter is worth waiting for, so the orchestrator needs the distinction to fail terminally instead of parking forever |
| `policy_dead_end(task, tool_name=…, profile=…, …)` | the same distinction for the **untagged** case: the effective allow-list when the policy/profile layers leave *no* routable provider, else None. Shares `_selection_order()` with `select_provider()` so the verdict cannot drift from the order actually walked |

**Fail-open is asymmetric.** A missing/unreadable/corrupt `policy.yaml` reaches `get_allowed_providers()` as "no restriction" — the same value a deliberately unrestricted policy produces (this is the provider side only: on the rule side an unreadable/corrupt file has held every queue task since 2026-10-08, see `policy.py` below; a missing one still classifies AUTO), and the file sits in a OneDrive-synced folder where that state is an operating reality, not a hypothetical. `dispatcher._allows()` splits it: fail-**open** for the capped providers (a lost policy must not take the orchestrator offline), fail-**closed** for `_UNCAPPED_PROVIDERS` = `{openrouter, vibe}`, the pay-per-token set that `_limits_ok()` reports as unconditionally available and that nothing else caps. One frozenset feeds both, so "no capacity gate" and "barred by default" cannot drift apart. An explicit allow-list naming them still authorises them. The section's *shape* is normalised too (`policy._coerce_provider_list`, `dispatcher._sanitize_allowed`): a scalar `dev-loop: claude` used to become `['c','l','a','u','d','e']` and a mapping its key list — both perfectly well-formed allow-lists matching nothing. **`_selection_order()`'s profile branch now calls `_allows()` too (fixed 2026-09-04)**, not just registration (`p in _providers`): before `profiles.py` derived `_KNOWN_PROVIDERS` from `_TAG_MAP`, `providers: [vibe]` was structurally impossible, so this branch never needed the fail-closed check. Once a profile could legitimately name an uncapped provider, the un-gated registration check alone routed to it whenever `allowed is None` — the normal state of an installation with no `tool_providers:` section. **The tag/forced branch followed on 2026-09-17**: `_selection_order()` and `forced_provider_policy_violation()` judge the forced provider with `_allows()` (the latter returns `_effective_allowed()` for the message), so a bare `#openrouter`/`#vibe` tag with no allow-list resolved is a terminal `provider_not_allowed` instead of a run. opencode stays fail-open.

**Forced providers are filtered too.** `select_provider()` used to prepend the forced provider *after* applying the policy filter, so `#openrouter`/`#vibe` walked straight past the exact filter meant to bar them. It now returns None with a `[policy]` log line — deliberately no fallback to another provider, because a silent swap hides which model did the work, which is worse than a clean stop in an unattended run.

**Opt-in providers.** `_TAG_MAP` also carries `#openrouter`/`#or_*`, `#vibe`/`#vibe_medium`/`#vibe_small`, and `#opencode`/`#opencode_*`, but `_PRIORITY` lists only `claude` and `codex` — all three pay-per-token providers are reachable by explicit tag only. All three are registered conditionally (`OPENROUTER_API_KEY` / `shutil.which("vibe")` / `OpencodeProvider.is_available()`) but `_limits_ok()` short-circuits to `True` for only two of them (OpenRouter, Vibe) since cclimits tracks no quota there. That short-circuit is the *definition* of "uncapped", which is why `_UNCAPPED_PROVIDERS` feeds both it and the fail-closed branch of `_allows()` — opencode is deliberately **not** in that set: its cap is pollable (a dedicated OpenRouter key, `limit: 5`/`limit_reset: "daily"`, measured 2026-09-04) via `openrouter_budget.fetch_budget()`, applied fail-closed by `limits._apply_opencode_budget_override()`, so `_limits_ok()` reaches its plain `getattr(limits, name).available` branch for it like any capped provider — and `_allows()` stays fail-**open** for it on a missing policy, same as claude/codex. `_limits_ok()` carries a third short-circuit for `gemini` when `GEMINI_API_KEY` is set (the REST API exposes no pollable quota) — dormant while the key stays commented out, and a thing to remember before re-enabling Gemini, since it would make Gemini uncapped without being in `_UNCAPPED_PROVIDERS`.

**`_NO_FALLBACK_PROVIDERS = {"vibe", "opencode"}`** (renamed from `_REVIEWER_ONLY` 2026-09-04 when opencode joined it — "reviewer-only" stopped describing a set containing a writing provider). Tag resolution normally uses `_providers.get(name)`, so a tag for an unregistered provider falls through to the default chain. That is fine for OpenRouter (executor replaced by executor) but wrong for these two, for two DIFFERENT reasons: Vibe is a non-writing reviewer, so a silent fallback would hand the job to a file-writing executor (blast radius); opencode DOES write, but the tag itself is the ask — avoiding Claude quota, or (customer code) the only ZDR-guaranteed path — so a silent fallback would defeat the point of tagging it at all, not widen a blast radius. `_tags_unregistered_no_fallback_provider(task)` returns the specific provider name (not just a bool) so `select_provider()`'s park log line names which one — "vibe fehlt" and "opencode fehlt" read as different problems in an unattended run. Precedence detail unchanged: an explicit forced provider (`resolve_forced_provider`) wins, so the guard only fires when no other provider was explicitly demanded.

## `git_commit.py`

Per-task auto-commit, added 2026-09-10 (committed early on 09-11; the dates in this repo name the
working day, not the commit timestamp). `commit_run_result(cwd, task, provider, snap_before,
snap_after=None, dirty_before=frozenset())` returns a
`CommitOutcome(branch, sha, files, skipped, error, skipped_paths, unrestored_paths)` and **never raises**
(outer `except BaseException`, with `KeyboardInterrupt`/`SystemExit` deliberately re-raised
BEFORE it — the same ordering rule `orchestrator.main()` documents, so a `#shutdown` task's
`SystemExit` cannot be swallowed by a commit attempt).

Sequence, all of it plumbing so **HEAD never moves**:

1. Preconditions, each a silent no-op with its own `skipped` code: `disabled`, `no_snapshot`,
   `not_a_repo`, `no_head`. A git binary that cannot be executed still returns "not a repo"
   (the conservative direction) but now logs a WARNING first — a systemic failure must not
   look like an expected skip.
2. `snap_after` (passed in by the caller, else `orchestrator._snapshot_dir` imported LAZILY —
   `orchestrator` imports this module at module level, so a top-level import here would cycle;
   `limits.py`'s lazy `dispatcher` import is the existing precedent).
3. Candidates = created ∪ modified ∪ deleted, `/`-normalised, `.git/` dropped. Over
   `GIT_COMMIT_MAX_FILES` → WARNING skip.
4. One `git status --porcelain -z -uall` for the whole repo (no pathspecs on the command line:
   Windows argv limit). `-z` is load-bearing — without it git octal-quotes non-ASCII paths and
   every filename with an umlaut silently drops out of the intersection. Candidates are
   cwd-relative, status is worktree-root-relative, so `git rev-parse --show-prefix` bridges the
   two. Rename/copy entries carry a second NUL-terminated origin field that must be consumed or
   every following entry parses one field short.
5. **The touchability rule.** Only paths whose index column X is `' '` or `'?'` (`_TOUCHABLE_INDEX_X`,
   an allow-list, so an unknown future status character is skipped rather than committed), and
   with no `R`/`C` in either column. Everything else is skipped, counted into `skipped_paths` and
   logged at WARNING. This one rule covers foreign staging, merge conflicts (`UU`) and renames.
6. The orchestrator's own bookkeeping files (queue, its `.lock`, `agent-queue-erledigt.md`,
   derived from `queue_manager.QUEUE_FILE`) are dropped — see the CLAUDE.md entry for why
   committing the queue file would re-open a finished task forever.
7. Commit: temp index via `GIT_INDEX_FILE` (child env is a COPY of `os.environ`; providers are
   shared singletons across threads), `read-tree <head_sha>` — the sha, never the symbolic
   `HEAD`, or tree and parent could describe different starting points — `git add -A` in
   argv-safe chunks (`_pathspec_chunks`, budgeted by BYTES with a count cap), `write-tree`,
   `commit-tree ... -F -` (message via stdin: a task text can carry quotes and newlines).
   Every pathspec is prefixed `:(literal)`; `--` ends option parsing but does NOT literalise,
   so a filename containing glob metacharacters would otherwise reach neighbouring files.
8. `update-ref refs/heads/<branch> <sha> ""` — empty oldvalue = create-only, `_2` suffix on
   collision, same pattern as `_git_snapshot`. All attempts used → `error="branch_collision"`
   and the worktree is left untouched (the dangling commit is gc'd; nothing is lost).
9. Cleanup, only after the ref exists: a SECOND `git status` first, and any path whose status
   changed since the first read is left alone (closes the destructive half of the race window).
   Then `git checkout <head_sha> -- <literal paths>` for tracked paths and `os.remove` for
   untracked ones — never `git clean -f`, which is in `SAFETY_DENY_PATTERNS` and would be a
   blunter instrument than an explicit, auditable list.
10. Success on `print` AND `logger` (`run_orchestrator.ps1` starts `--watch` without stdout
    redirection).

Caller: `orchestrator._commit_run_changes()` owns the WHETHER (the `#no-commit` tag, the
read-only-tool gate, containment of anything that escapes) and `_with_commit_note()` puts the
commit line in FRONT of the change summary, because `notifier.notify_task_done` truncates that
field to 500 characters and an appended branch name is exactly what a large diff would cut off.

## `queue_manager.py`

Obsidian MD queue parsing with sidecar `.lock` file locking (msvcrt on Windows, fcntl on Unix). Regex-based metadata extraction (`cwd:`, `#tool:`, `#agent:`, `#parallel`, `#claude_*`, `#id:`, `#needs:`, `#pass1:`, `#pass2:`, etc.). `extract_pass_providers()` returns `{1: "claude", 2: "gemini"}` for cross-provider tool support. UTF-8 with cp1252 fallback. Smart wikilink/file context injection with TF-IDF section extraction; the 7 500-char budget (`PROMPT_WIKILINK_TOKENS` × 5) is split by `_share_budget()` across **only the refs that resolve and read**, smallest need first, so an unresolvable ref no longer claims a share (fixed 2026-08-28). All of `collect_file_context()` reports through `logger`, not `print`. `_parse_subtask_line()` shared helper used by both `read_queue_items()` and `_replace_open_task_line()`. Subtask-aware task matching in queue mutations (mark_done/mark_retry/finalize) prevents wrong-task collisions in parallel queues. Two-pass dependency resolution in `read_queue_items()`: Pass 1 collects open tasks, Pass 2 resolves `#needs:` deps against completed IDs (`_collect_completed_ids()` scans `[x]` and `[-]` lines but skips a `[x]` carrying the terminal-failure stamp ❌ — `line_is_failed()`). `mark_done()`/`finalize_task_with_result()` take `failed=` and share `_completion_line()`; `_DONE_TASK_TS_RE` archives ✅ and ❌ lines alike. Blocked tasks get `QueueTask.blocked_reason != ""` and are skipped by `run_once()` without marking done.

**`MODEL_TAG_RE` covers all 23 model aliases (fixed 2026-08-15 for the original 20; found 2026-07-23; opencode's three ZDR aliases raised it to 23 on 2026-09-04).** The alternation is built from `dispatcher._TAG_MAP` — every key whose tag text does not equal its own provider name (i.e. every model-specific alias, not the six bare provider-selection tags) — sorted longest-first so a prefix alias (`codex_5`) cannot shadow the longer alias it prefixes (`codex_5_4`). `extract_model_tag()` therefore now resolves `#gemini_flash_lite`, `#codex_5`, `#codex_5_4`, `#vibe_medium`, `#vibe_small`, all nine `#or_*` tags, and `#opencode_deepseek`/`#opencode_deepseek_long`/`#opencode_glm` too, not just the original six. `queue_linter.py` calls the same extractor, so its cross-provider leakage check (`model_provider_mismatch`) now also covers those. Regression test: `tests/test_queue_manager_regressions.py::test_model_tag_re_covers_every_dispatcher_alias`.

## `providers/vibe.py`

Mistral Vibe CLI — second non-Claude voice next to Codex, and the queue-side counterpart to the interactive workflow's stage-2 reviewer. Registered only when `shutil.which("vibe")` finds the binary (`VibeProvider.is_available()`), and kept out of `dispatcher._PRIORITY`, so it runs only on an explicit `#vibe`/`#vibe_*` tag or as a `#second_opinion:` value. `_limits_ok()` short-circuits it like OpenRouter (pay-per-token, no cclimits quota); `--max-price` (`config.VIBE_MAX_PRICE_USD`) is the per-run cost ceiling vibe enforces on itself.

**Reviewer, not executor.** `read_only=True` → `--disabled-tools "*"` (pure reasoning over the piped prompt, `VIBE_READONLY_MAX_TURNS=1`). Otherwise `--enabled-tools read_file --enabled-tools grep` and nothing else — never `bash`/`edit`/`write_file`, and never `--auto-approve` (both read tools are `permission = "always"` in vibe's config, so no approval prompt can stall a headless run). This is a deliberate policy choice, not a CLI limitation.

The same policy is enforced one level up in `dispatcher._NO_FALLBACK_PROVIDERS`: a task that tags `#vibe` while Vibe is *not* registered yields **no provider at all** (`select_provider` → `None`, task parked) instead of falling through to the default chain. For an unregistered `#or_*` tag that fall-through is harmless — executor replaced by executor — but silently answering "review this without writing" with a file-writing executor widens the blast radius past what the task asked for.

**Read confinement — measured, not assumed (2026-07-23).** With `--trust` + `--workdir X`, `read_file` reads files inside X, and refuses both an absolute path outside X and a `../` traversal (positive control included: the in-workdir read succeeded in the same session). So the working directory is the read boundary; no writing tool is enabled in either mode.

**CLI facts, all verified against vibe 2.22.0 (2026-07-23) — each one silently breaks the run if dropped:**
- **`-p` with no value reads the prompt from stdin.** Task prompts here reach ~100 KB; as an argv element that would exceed the Windows command-line limit (8191 chars under cmd.exe). Verified with an 808 KB prompt whose marker was on the last line. This also puts vibe under the same `_StdinDelivery` contract as the other CLI providers — `stdin_incomplete` handling is copied from `codex.py` verbatim, including the "real error wins at `rc != 0`" ordering.
- **`--trust` is mandatory** — without it the CLI blocks on the trust prompt for an untrusted cwd (`~/.vibe/trusted_folders.toml` lists the vault as untrusted) and the run hangs at 0 % CPU with no output.
- **There is no `--model` flag.** The model lives in `~/.vibe/config.toml` (`active_model`) and is overridable per process via `VIBE_ACTIVE_MODEL`, whose value is a vibe *alias* (`mistral-medium-3.5`, `devstral-small`), not a raw model name. An unknown alias falls back to the default **without an error** — hence `config.VIBE_MODEL_ALIASES` as the single source of those strings.
- **`PYTHONUTF8=1` in the child env** — vibe is a Python CLI and dies with a `charmap` codec error writing non-ASCII output under a Windows cp1252 locale.
- **`shell=False`** — real `.exe` on PATH (uv tool shim), not an npm `.cmd` wrapper, so no cmd.exe quoting sits between us and the argv.
- **No usage data.** `--output json` echoes the full message list including vibe's multi-KB system prompt and still carries no token or cost fields, so text mode (stdout = the final answer, nothing else) is strictly better. `RunResult` leaves the token fields at 0 and the orchestrator's char/duration estimation takes over, same as Codex.

Model forcing goes through `run_with_watchdog(..., env=…)`, which passes a **fully merged copy** of `os.environ` to `Popen` (Popen replaces the environment, it does not merge). Building that copy in the provider rather than mutating `os.environ` is load-bearing: providers are shared singletons driven from `parallel_runner` threads, so an in-place mutation would leak one run's model into a concurrent run.

## `providers/opencode.py`

Fourth non-Claude voice (opencode CLI, Stufe 2 — tag-activated only, `_NO_FALLBACK_PROVIDERS` member, deliberately kept out of `_PRIORITY` for the still-unmeasured Stufe-3 hang cause). `OpencodeProvider.is_available()` requires BOTH a resolvable `opencode.exe` (never the `.CMD`/`.ps1` npm shim — `subprocess` can only start a `.cmd` via `shell=True`, and a quote embedded in a task prompt then breaks out of cmd.exe's quoting, measured 2026-08-21) AND both agents this repo depends on (`extern-review`/`extern-dev`) present in `opencode.json`.

**Prompt delivery is a real file via `-f`, never stdin** (`input_text=None` to `run_with_watchdog`) — this structurally removes the whole `stdin_incomplete` tail-loss contract every other provider carries, because there is no pipe to lose the tail of. `-f` is a yargs ARRAY flag, so the short instruction message (`_SHORT_MESSAGE`) must sit BEFORE it in argv or it gets swallowed as a second filename; the message itself just tells the agent to read the attachment fully, since it is the only part of the run guaranteed to arrive uncut. `config.OPENCODE_MAX_PROMPT_BYTES` (default 50 000) caps the `-f` file in BOTH read_only and write modes, enforced before any subprocess call — above it: `RunResult(success=False, error="prompt_too_large")`, never silent truncation. Not caution for its own sake: a `-f` file outside `--dir` cannot be reread by either agent (`external_directory: deny` is the LAST matching rule in opencode's permission list, measured 2026-09-04 against even the seemingly-allowed `%TEMP%/opencode/*` path), so above the cap the honest alternative to failing is a reviewer silently judging a truncated fraction of the material — exactly what a 2026-08-28 measurement showed (24 % of a 222 KB file arrived, 5 of 6 anchors missing).

**Model resolution**: forced tag (`#opencode_<alias>`, pre-validated via `config.model_id_for_provider()`) > `OPENCODE_MODEL_PICKER` (optional external script, `~/.claude/scripts/oc_pick_model.py --profile $OPENCODE_PICKER_PROFILE`, 90 s timeout, discarded on non-zero exit or non-single-token stdout) > `config.OPENCODE_DEFAULT_MODEL`. The picker being absent is the NORMAL case on a fresh machine, not a degraded fallback. `--variant <effort>` passes `#effort:` values through raw (no mapping table — `--variant xhigh` exits 0, undocumented values are tolerated).

**Error classification** scans ANSI-stripped text for keywords, because `exit 1` is ambiguous (an unknown model alias and a real API failure both exit 1 with a generic message): `"data policy"`/`"zero data retention"` → `error="policy_block"` (NOT transient — a ZDR refusal cannot be retried away) and rate-limit/402 keywords → `error="rate_limit"` read combined stdout+stderr; `401`/`403`/`"invalid api key"` → `error="auth_error"` reads **stderr only**. The asymmetry is deliberate and was measured on 2026-09-04: stdout carries exclusively the agent's answer, stderr exclusively opencode's own protocol, and `unauthorized`/`forbidden`/`HTTP 403` are among the most common words in a security review — so scanning the answer for them mislabels a run by its own content. It only ever bought a label anyway: no consumer of `auth_error` exists outside `taxonomy.py`, and an unclassified error reaches the same non-transient outcome via `error_code_of() == ""`. What a misclassification really costs is a second paid run — `orchestrator.py:1187` leaves the in-run backoff early for `TRANSIENT_ERRORS` only, so `rate_limit` means one attempt and every non-transient code means `MAX_RETRIES_PER_PROVIDER` (2). That is why `rate_limit` stays generous (only digit boundaries; the 402 phrase list is multi-word so a bare "credits" in prose cannot fire it) while auth is strict. Otherwise stderr passes through as the error, with the agent's answer kept in `RunResult.output` — putting it in `error` (as the first version did) would have shipped a whole review into the field that gets logged, notified truncated at 3500 chars, and stored as the failure reason, while the field the orchestrator persists as the result stayed empty. stdout carries raw ANSI escapes, stripped before classification and before `RunResult.output`. No token/cost numbers are reported (`cost=0` in 142/142 measured log lines) — the orchestrator's char/duration estimate takes over, same as Codex/Vibe. After an idle or hard kill, a `logger.warning` flags a possible orphaned `opencode.exe` holding its SQLite session DB open — no sweeper is built (unmeasured whether `process_runner._tree_kill`'s double `taskkill /F /T` already covers it).

## `providers/process_runner.py`

Liveness/hang watchdog shared by all four CLI providers (DRY). `run_with_watchdog(cmd, *, input_text, cwd, idle_timeout, hard_timeout, shell, liveness_lines=False, env=None, stdin_via_file=False, ...) → WatchdogResult` (CompletedProcess-compatible via `returncode`/`stdout`/`stderr`, plus `stdin_error`).

**`env`** is passed straight to `Popen`, which **replaces** the child environment rather than merging it — callers must hand over a fully merged copy of `os.environ`, never a delta. Building that copy per call (as `providers/vibe.py` does for `VIBE_ACTIVE_MODEL`) instead of mutating `os.environ` is load-bearing: providers are shared singletons driven from `parallel_runner` threads, so an in-place mutation would leak one run's model into a concurrent run.

**stdin delivery verification (`_feed_stdin` / `_StdinDelivery`):** `_spawn` opens stdin with `text=True` → a buffered `TextIOWrapper`, so `write()` only fills the buffer and the *tail* is flushed by `flush()`/`close()`. A failed tail flush therefore truncates the END of the prompt — and `orchestrator._build_prompt` assembles `core → skills → memory → task`, i.e. the task text sits last. Result: the CLI answers a context-only prompt ("what would you like me to do?"), exits 0 with a `subtype=="success"` result event, and the run used to be finalized as a SUCCESS that did nothing. Observed 5× (2026-07-14/15/20), cost 3 days of vault health data. `_feed_stdin` now flushes explicitly before closing (so the tail flush is its own attributable failure site), logs via the module logger, and records the outcome in `_StdinDelivery`. **Fail-closed:** `delivered` is set ONLY after a successful `close()`; a caught error, an uncaught exception class (`MemoryError`, `RuntimeError` at shutdown) and a thread that never finished all count as failed delivery. `run_with_watchdog` reads it after the joins and surfaces it as `WatchdogResult.stdin_error`; the timeout path attaches it to the raised `TimeoutExpired` as `exc.stdin_error`. **Blind spot — why detection alone was not enough:** the feeder confirms delivery from the WRITE side only. A prompt that fits under the OS pipe buffer (~64 KB) — OR the ≤64 KB *tail* of a larger prompt once the child stops reading — lands in the kernel buffer, so `write`/`flush`/`close` all succeed and NO `stdin_error` is raised even though the child never consumed those bytes. This is not merely a small-prompt edge. **Correction 2026-07-25:** the morning-brief incidents (20./24./25.07.) were previously attributed to exactly this tail loss — that attribution is **disproven**. The prompts that actually arrived were measured from the Claude Code session files: success and failure runs are structurally identical (22.026–22.888 chars, not ~70 K tokens) and the task text was fully present in **all** of them, at 61–64 % of the prompt rather than at the end. The real defect was the prompt LAYOUT (see [ADR-002](../adr/002-task-last-in-prompt.md)); `_build_prompt` now appends the task last under `## Aufgabe`. The blind spot described above is real for the feeder path and worth guarding — it just was not what broke the morning-brief.

**File-based delivery (`stdin_via_file`, `_write_temp_prompt`):** when set, `run_with_watchdog` writes `input_text` to a temp file (UTF-8, `newline=""`), opens it read-only and hands it to the child as stdin — no feeder thread. The whole prompt is on disk before the first read and the child reads to a real end-of-file, so there is no buffered close/flush race and no dependency on the OS pipe buffer size; the tail cannot be lost. **Delivery is verified, not assumed** (`_verify_prompt_file`): the byte count on disk is compared against `len(input_text.encode(encoding))`, and a mismatch, an empty payload or an unreadable file surfaces as `stdin_error` exactly like a feeder failure. Until 2026-07-25 this path instead set `delivered = True` unconditionally ("True by construction"), which pinned `stdin_error` to None for every caller and made the detection in `claude.py` dead code — a safety net that could not fire. The temp file is closed + unlinked in the `finally` on every path (success, kill, spawn failure). **The claude provider opts in** (`providers/claude.py`, together with `shell=False`); the piped feeder + `stdin_error` detection stays the default for Codex/Vibe, which have no observed incident — widening it to them is a separate change with its own blast radius.

**Provider contract:** all three CLI providers read `getattr(result, "stdin_error", None)` — `getattr` because the provider tests fake this object with a three-field `SimpleNamespace` — and turn it into the **bare code** `stdin_incomplete` (exact-equality matching is the repo-wide convention; detail goes to `output`). It is applied in exactly two places, never up front: **(1) inside the success branch** — a run that would otherwise be booked as success, which is the incident shape — and **(2) as a last resort at `rc == 0`** when no better classification matched. Ordering is load-bearing in BOTH directions: a child dying early (rate limit, missing session, "not logged in", a panic) ALSO breaks the pipe because the prompt (~100 KB) dwarfs the OS pipe buffer, so checking too early masks the real cause, while trusting the fallback at `rc != 0` sweeps ordinary CLI crashes into the stdin path. At `rc != 0` the real error therefore always wins; the delivery diagnosis is carried alongside it — appended to `output` on the generic fallback (the keyword returns for `rate_limit`/`session_missing`/`unreachable` keep their bare shape), and always present in the `process_runner` log.

**Reach — known limits.** The guarantee covers single-shot queue tasks. It does NOT extend to: (a) `#parallel` parents, which `orchestrator.py` finalizes regardless of subtask success, so a truncated subtask prompt closes the parent anyway; (b) multi-phase tools that translate a provider error into their own `phase*_failed` code and lose `stdin_incomplete` on the way. Both are pre-existing behaviours for every error code, not specific to this one — widening them is a separate change with its own blast radius.

**Orchestrator reaction:** `stdin_incomplete` is in the `_run_with_retry` bail-out list — retrying the same oversized prompt down the same pipe within one run is pure token burn (~26k cache_creation tokens per attempt). Beyond that it is deliberately **not** special-cased and takes the generic error path (5-min provider cooldown + rotation), which is bounded and self-healing: once all providers are cooled, `select_provider` returns None and the task is parked via `mark_retry`. An earlier attempt to skip cooldown+rotation — motivated by the fact that a local pipe fault says nothing about provider health and all providers share the feeder — removed that throttle without replacing it and produced an unbounded 30-second retry loop. Revisiting this needs the `hang` treatment (persistent counter in the queue line, backoff, BLOCK after N), not a bare `break`. **Analytics caveat:** because the single-shot path rotates providers, its replay record is written as `provider_unreachable` once all providers are exhausted — so `CAT_STDIN` shows up in the dashboard mainly for forced-provider and tool tasks. The real code still reaches Telegram (`notify_error`) and `orchestrator.log`. Do not "fix" this by special-casing the error in the orchestrator; that is exactly the reflex that produced two P1 regressions.

**Why:** plain `subprocess.run(..., timeout=)` only kills the direct child; on Windows with `shell=True` the real node/claude grandchild is orphaned, keeps stdout pipes open and `communicate()` blocks until the orphan finishes (observed: nominal kill 900 s, return 1094 s).

**Threading model:** `Popen` + TWO daemon reader threads draining stdout AND stderr simultaneously (a single reader deadlocks on a full OS pipe buffer of the other stream) + one daemon stdin feeder **on the piped-delivery path only** (`stdin_via_file=True` hands the child a temp file as stdin and starts NO feeder — see the file-based delivery note above). Readers use the underlying buffer's `read1()` (byte-granular) + a `codecs` incremental decoder, NOT line iteration — a line iterator only registers activity on a newline, so a newline-less progress burst (build logs, `pytest` dots) would look idle and get false-killed. The watchdog loop (`_watchdog_loop`, 0.5 s poll) returns `"idle"` (no activity for `idle_timeout`) or `"hard"` (`hard_timeout` elapsed); on either it tree-kills the process, joins readers (5 s timeout — the kill closes the orphan FDs so readers get EOF), and raises `subprocess.TimeoutExpired` with an extra `timeout_kind` attribute. daemon=True is the backstop if an FD stays open. A `try/finally` closes `proc.stdout/stderr/stdin` after the joins on every path (success and kill) — `subprocess.run` did this via its context manager; without it each call leaks 2-3 pipe FDs → exhaustion in `--watch`. Each reader caps its retained sink at `_MAX_CAPTURE_CHARS` (~8 MB, oldest lines dropped first, tail kept so the final `result` line survives) — `stream-json --verbose` streams every `tool_result` (full file reads, Bash output) as its own event, so an uncapped sink could hold hundreds of MB on a long phase.

**Tree-kill (`_tree_kill`):** Windows `taskkill /F /T /PID` fired twice (belt-and-suspenders against a grandchild forking between `poll()` and enumeration); POSIX `os.killpg(SIGTERM)` → grace → `SIGKILL` (process spawned with `start_new_session=True`). Always `proc.wait()` afterwards so no zombie remains.

**Liveness model (`_Liveness`):** byte mode (Gemini/Codex, `liveness_lines=False`) touches last-activity per stdout/stderr line. NDJSON-event mode (Claude, `liveness_lines=True`) parses each stdout line. **There is NO top-level `{"type":"tool_use"}` event** (verified claude 2.1.158, Win11) — tool activity lives in the *content blocks* of `assistant`/`user` events. `_Liveness.on_event(evt, now)` inspects `message.content[]` via `_content_blocks()` and tracks a **SET of open `tool_use` ids** (`_open_tool_ids`, plus an `_anon_open` counter for blocks lacking an `id`): an `assistant` event adds each `tool_use` block's `id`; a `user` event discards each `tool_result` block's `tool_use_id`; the top-level `result` event (`_TOOL_DONE_EVENTS`) clears all. `idle_for()` returns 0 (idle timer paused) while the set is non-empty. A set rather than a single boolean is essential: Claude emits **parallel** `tool_use` blocks in one assistant message and spawns `Agent` subagents, so the first `tool_result` must not resume the timer while a sibling tool is still running (would false-idle-kill a productive run). A `threading.Lock` guards the multi-step set updates against the watchdog reader. Real sequence: `system/init → rate_limit_event → assistant[thinking] → assistant[tool_use] → (stdout silence for the tool duration) → user[tool_result] → assistant[text] → result`. This is load-bearing: a single blocking tool call holds stdout silent for its whole duration (verified 12 s tool → 18.1 s inter-line gap, scales with tool duration), so a naive byte watchdog would kill a productive pytest/build/install phase. `hard_timeout` stays the absolute backstop. Constants: `_POSIX_TERM_GRACE_SEC=5`, `_WATCHDOG_POLL_SEC=0.5`, `_READER_JOIN_TIMEOUT_SEC=5`, `_TASKKILL_TIMEOUT_SEC=10`.

## `providers/gemini.py`

**Dual-mode** since the consumer Gemini CLI (Code Assist for individuals / AI Pro / AI Ultra) was shut down 2026-06-18.

**HTTP-API mode (`GEMINI_API_KEY` set, preferred):** calls the Google Gemini REST API directly via `urllib.request` (stdlib, like `openrouter.py`) — `POST {GEMINI_BASE_URL}/models/{model}:generateContent` with `x-goog-api-key` header. The whole `task` (which already carries the system prompt + SAFETY_RULES from `get_system_prompt`) is sent as the single user turn — no separate `systemInstruction` (would duplicate safety). Output from `candidates[0].content.parts[].text`; tokens from `usageMetadata` → `promptTokenCount`=input, `candidatesTokenCount + thoughtsTokenCount`=output (gemini-3.x are thinking models; thinking is billed as output), `cachedContentTokenCount`=cache_read. `GEMINI_MAX_OUTPUT_TOKENS` (default 16384) sized so heavy thinking doesn't starve the visible answer. **Legacy CLI mode (no key):** Standard/Enterprise subscription users retain CLI access — `--yolo` full tool access, `--approval-mode default` read-only, `--model <id>` forced, through `run_with_watchdog` byte-only (`CLI_IDLE_TIMEOUT_NO_LIVENESS_SEC`); `timeout_kind` maps idle→`hang`, hard→`timeout`.

**Retired from every active path (2026-08-15).** Both modes above are still implemented and still work if re-enabled, but nothing routes here: `gemini` is out of `dispatcher._PRIORITY`, out of `policy.yaml`'s `tool_providers`, and `GEMINI_API_KEY` is commented out in `.env`. Trigger was an `IneligibleTierError` on the remaining tier plus data-protection concerns about sending review content through the HTTP API.

The availability machinery below is therefore **dormant, not deleted** — and it is the reason the commented-out key matters rather than being cosmetic. In HTTP mode the public REST API exposes no pollable subscription quota, so availability was cooldown-driven: `dispatcher._limits_ok("gemini", …)` returns `True` whenever a key is set, `limits._needs_token_refresh` skips the dead CLI/OAuth refresh, and `limits._apply_gemini_http_snapshot`/`_apply_gemini_http_override` report a synthetic available snapshot instead of the cclimits quota — the same treatment as OpenRouter. With a key set, Gemini is thus an *uncapped* provider that is **not** in `dispatcher._UNCAPPED_PROVIDERS`, so it would not inherit the fail-closed policy default the other two uncapped providers get. Anyone re-enabling Gemini has to decide that question deliberately.

It raises `ValueError` when the answer cannot be known — the file exists but did not parse into a mapping (`_load_error`, set by `_load_rules_locked`, cleared by the next good parse; rules and the other sections keep their last good state), or the tool's entry is not a mapping — so a caller guarding a safety switch can fail closed. `_load_error` is cleared only after EVERY section has parsed (K6, `_apply_sections_locked`): a section parser that raises (`stop_conditions: 1` → `TypeError` in `_parse_tool_contract`) records it and re-raises. The call whose reload hits a failing section parser raises that same error instead of the parser's raw exception, so one fault has one text (run_once() throttles its alert per text). While `_load_error` is set, `_reload_if_changed` skips the mtime shortcut — the mtime is stored before parsing, so a repair that keeps the mtime (OneDrive sync, coarse resolution) was never read again; an unchanged broken file is re-parsed per call, logged at DEBUG (`_record_load_error_locked` warns only on a new error text) and its section error is not re-raised. ## `harness_index.py`

Incremental SQLite index (2026-10-09) over five local sources — Claude Code transcripts (`HARNESS_CLAUDE_PROJECTS_DIR`, main files `<proj>/<session>.jsonl`, subagent runs `<proj>/<session>/subagents/agent-<id>.jsonl` + `.meta.json`), Codex rollouts (`HARNESS_CODEX_SESSIONS_DIR`), `opencode.db` (`HARNESS_OPENCODE_DB`, `session` and `message` only, `mode=ro` + `PRAGMA query_only`, never `immutable=1`, never `part`), the extern-voice ledger and the harness-change markers — into `HARNESS_DB_FILE` (`logs/harness-index.sqlite`, WAL). Run as `python -m harness_index --update`; the orchestrator never runs it in-process: `dashboard.start_autostart()` starts the daemon thread `harness-index-scheduler`, which calls `run_update_subprocess()` first after `HARNESS_FIRST_RUN_DELAY_SEC` (60 s) and then every `HARNESS_UPDATE_INTERVAL_SEC` (1800, 0 = off). The child runs with `sys.executable -X utf8`, cwd = directory of `config.py`, Windows `BELOW_NORMAL_PRIORITY_CLASS | CREATE_NO_WINDOW` from the parent plus `PROCESS_MODE_BACKGROUND_BEGIN` set by the child on itself (lowers I/O and memory priority too, and caps the working set at about 32 MB — not documented by Microsoft, described by B. Dawson, randomascii 2023-10-01; beyond the cap pages come back as soft page faults, so a run takes longer, the measured Windows first run took 51.7 s; `GetPriorityClass` read NORMAL in this mode although the parent started the child BELOW_NORMAL, so `_lower_priority_windows` sets BELOW_NORMAL again whenever the class reads higher — the CPU class is never above BELOW_NORMAL, and a Windows-only test checks that background mode survives it: a second `PROCESS_MODE_BACKGROUND_BEGIN` must fail with error 402), POSIX `os.nice(10)` from inside the child (no `preexec_fn` — not thread-safe), and is killed through its own `Popen` handle after `HARNESS_LOCK_STALE_SEC`. A failure is one warning per distinct message (no repeat every 30 min), a recovery one info line; the child's stderr (full error texts, which the database does not keep) is logged as one info line after each run (`run_update_subprocess` returns its last 2000 characters as `stderr`). The index thread does not depend on the dashboard's bind.

**Natural keys (idempotence):** Claude `message.id` alone, across ALL files (schema 2, Korrekturrunde 1 — schema 1 keyed `(file, message.id)` and counted an id once per file — measured by the Auftraggeber: 101 ids in more than one file, all of them subagent transcripts of the same parent session, ≈ 0.1 % of the tokens; main+subagent and main+main: none). One API answer is split into up to four transcript lines whose `usage` is NOT identical (measured by the Auftraggeber on real data: 57 % of the multi-line ids differ in at least one counter, streaming); the upsert takes `max()` per counter, never a sum, and a `main` row would take the attribution (`file_key`, `session_id`, `kind`, `agent_id`, `origin`) over a subagent row (rule from the spec; not observed on real data) — SQLite's `DO UPDATE SET` expressions see the OLD row, so the `CASE` reads `kind` before it is overwritten. Subagent runs `(sessionId, agentId)` from the meta file, linked to the calling `tool_use` via `toolUseId`. Agent calls `tool_use.id` (`name` `Agent` or `Task`; `input.model` missing → `Standard`). `cost-state` the line with the HIGHEST `cost_usd` per `sessionId` (main files only; the other fields come from that line), day = local day of `startTime`. Agent meta files take their day from the calling `claude_agent_call` (via `toolUseId`), not from the file's mtime. Codex one row per rollout file with the LAST `token_count` whose `info` is not null (cumulative `total_token_usage`) plus the newest `rate_limits` (`info: null` lines still carry those). opencode `message.id` / `session.id`, read above a `time_updated` watermark with 5 s overlap; rows whose `time_updated` did not change are not counted as read; an unparseable `data` is remembered with `role NULL`. A message without `time.completed` (`completed = 0`) is re-read on every run for `OPENCODE_INCOMPLETE_RECHECK_MS` (2 days) even when its `time_updated` did not move, in chunks of 500 ids. Ledger: the LINE number (schema 2) — every line is one call, two lines with the same second, voice and repo are two calls; the whole file is hashed every run (`_read_small_file`, a few KB) and on any change the table is rebuilt from scratch (an edit of the same length in the middle leaves no ghost; a deleted ledger keeps the table). **Deleted source files stay in the index, on purpose:** Claude Code removes old transcripts itself; the index keeps their numbers as an archive, so a recount against the disk after such a deletion comes out LOWER on the disk side (measured Korrekturrunde 3: 10 deleted Claude files, 115 messages) — that difference is not an indexing error. Markers `(date, id)`, the table is replaced whenever the marker file's whole-file hash changes (a corrected date must not leave a ghost), kept when the file is deleted.

**Incremental reader:** per file size, mtime, offset of the last complete line, a head fingerprint (sha256 of the first `min(256, size)` bytes at the last read) and a tail fingerprint (sha256 of the up to 256 bytes right before the offset — catches a file rewritten in place with the same head, where the old offset would land in the middle of a new line). Size and mtime unchanged → not even opened (`_unchanged`, one `stat`), no transaction. Smaller than the offset or a different head → read from the start (keys absorb it). A line without newline waits (the offset stays in front of it) while the file is younger than 60 s. Once the file has been quiet that long, the rest is settled exactly once: valid JSON is counted, anything else is counted as skipped, and the offset moves to the end of the file (`_iter_new_lines`). A file with a young open rest is opened again on the next run (`_unchanged`), one with a settled rest is not. Known limit: if the writer completes such a rest only after more than 60 s, both halves end up in the skipped counter and nothing is counted twice; Claude Code and Codex write each line in one write, so this does not happen in practice. A complete line that does not parse — or fails in ANY way while being parsed or stored (`Exception`, counted per exception type in `skipped_by_type`; the parse sits inside the same `try` since Korrekturrunde 2, because a deeply nested line raises `RecursionError`, not `ValueError`, and used to roll the whole file back on every run; the `.meta.json` files and the marker lines are skipped the same way, and a deeply nested quiet tail is simply not evaluated yet instead of aborting the file) — counts as skipped and the offset moves on. Every handled line runs inside `SAVEPOINT line` with a copy of the file's in-memory `info`: a line that raises leaves neither rows (e.g. the agent call of a line whose usage then held a number out of range) nor file info behind; a Codex line's values reach the rollout row only once the whole line succeeded. Cost, measured on Linux with a dense synthetic load (500 000 small assistant lines in 20 files, three runs each, the run's own duration): first run 7.3–8.0 s without, 9.0 s with the inline SAVEPOINT (+16 %; as a context manager it was 10.1–10.6 s, +35 %); incremental runs read a few lines; only `sqlite3.OperationalError` and a bare `sqlite3.DatabaseError` (the index itself is broken or locked) abort the file. Integers outside ±(2⁶³−1) raise `_OutOfRangeError` (SQLite would otherwise raise `OverflowError` for the whole file), timestamps before 1970 or unparseable give no day (line skipped). A file that fails as a whole is one error entry and leaves every other file's offset alone (`_guard_file`). One transaction per file (rows + state). Files older than `HARNESS_WINDOW_DAYS` (mtime) are skipped. Deleted source files keep their rows (the heartbeat deletes orchestrator transcripts after 14 days). Pre-filter: a compact line without the needles (`"type":"assistant"` …) is skipped unparsed, a line in any other format is parsed.

**Origin:** main file `entrypoint` (first line that has one) `cli` → `interaktiv`, `sdk-cli` → `orchestrator`, missing or anything else → `unbekannt`. Subagent rows are `kind='subagent'` and carry the PARENT session's origin (own field only if the parent is unknown). ## `limits.py`

`cclimits` wrapper for provider capacity checks, OAuth refresh handling. Direct `cclimits` invocation (no npx); disk-cache via `--cache-ttl 600` limits API calls to ~6/h.

**Polling-Intervalle**: `_BG_POLL_IDLE_SEC=600` (10 min, queue empty) — matches `cclimits --cache-ttl=600` so each idle poll bypasses the disk cache and hits the real API; `set_queue_idle(False)` wakes the bg thread on task arrival so the cache is fresh before the next task starts. `_BG_POLL_AVAILABLE_SEC=300` (5 min, queue active) — covers within-batch drift between consecutive tasks in run_once; rate_limit errors trigger `get_limits(force_refresh=True)` synchronously, so cache staleness can never delay error recovery.

`set_paused(True/False)`: while paused the bg refresh thread skips all cclimits calls and only wakes on resume — `run_watch()` calls this around its `/pause` wait so the orchestrator stops burning the monitoring quota during user-pauses.

HTTP 429 resilience: (tier 0) local JSONL fallback via `claude-monitor` (no HTTP, `CLAUDE_PLAN` env var), (tier 1) snapshot cache with estimated usage tracking, Telegram notifications on 429 start/clear. During the snapshot-cache fallback, per-task estimated usage is split across Claude's 5h/7d windows by calibrated `tokens_per_pct` ratios (`_estimate_window_usage_calibrated` — see `quota_state.py` below) rather than the reset-time heuristic; uncalibrated providers keep the heuristic.

**`AllLimits.opencode`** is NOT from `cclimits` — opencode has no OAuth quota, it pays per token through an OpenRouter key. `_apply_opencode_budget_override()` fills it from `openrouter_budget.fetch_budget()` (live HTTP, same override pattern as `_apply_gemini_http_override()`, applied last in `_get_limits_fresh()` so nothing above can clobber it) and is deliberately **fail-closed** — the opposite of Claude/Codex's fail-open default: a stale/unknown Claude capacity risks nothing extra (subscription quota), a stale/unknown opencode capacity risks real spend, so "don't know" collapses to `available=False`. **Registrierung wird ZUERST geprüft, vor jeder Budget-Abfrage** (2026-09-04, interner Quality-Pass): das Budget hängt am OpenRouter-Key und beantwortet deshalb auch auf einer Maschine ohne opencode-Binary „ist Geld da" mit ja — `available=True` wanderte damit in Aggregate, die etwas anderes bedeuten. Gemessen mit claude/gemini/codex auf `False`: `any_available()` kippt von False auf True (`run_watch` schläft 30 s statt bis zu `SLEEP_POLL_INTERVAL*10` und startet jede Runde einen echten `cclimits`-Subprozess), `_compute_next_poll_sec` geht von 30 auf 300 s, und `earliest_reset_sec()` nimmt ein `min()` über opencodes **angenommene** UTC-Mitternacht, kann also Retry-Zeitpunkt und `notify_providers_exhausted`-Meldung für einen Provider bestimmen, auf den nichts routen kann. `_opencode_budget_snapshot()` liefert deshalb ohne registrierten Provider sofort `available=False, error="not_registered"` — und spart nebenbei den HTTPS-Roundtrip bei jedem Refresh auf Maschinen ohne opencode. Der `dispatcher`-Import ist bewusst lazy (dispatcher importiert limits auf Modulebene → Zyklus). `_opencode_budget_snapshot()`: `remaining is None` (fetch failed OR the key structurally has no cap — `fetch_budget()` cannot tell those apart, see its docstring) → `error="budget_unavailable"`; `available = remaining > config.OPENCODE_MIN_REMAINING_USD` (default 0.25, sized off the most expensive curated review measured, ~$0.195, so it leaves one full run of headroom) — comparison is strict `>`, not `>=`. `_opencode_reset_epoch()` turns the API's cadence string (`"daily"`/`"weekly"`/`"monthly"`, no reset timestamp given) into an absolute epoch under the ASSUMPTION of a UTC-midnight reset — flagged as an assumption in the code, and it only feeds `earliest_reset_sec()`'s backoff timing, never `available` itself, so a wrong guess delays a retry rather than risking spend. Three `AllLimits` aggregate methods (`earliest_reset_sec`, `any_available`, `has_transient_token_refresh`) enumerate the provider fields **by hand** — the exact drift source that bit this addition once already (the plan that introduced the field only remembered two of the three) — so a `tests/test_limits_opencode.py::test_all_limits_drift_guard_covers_every_field` iterates `dataclasses.fields(AllLimits)` and fails loudly if a future field is missing from any of the three. `_providers_with_429()` and `_apply_429_fallback()` deliberately do NOT enumerate opencode — both work purely off cclimits' raw JSON, and opencode was never a cclimits provider to begin with; its own rate-limit handling lives in the provider's own error classification, same as Codex/Vibe.

**`all_provider_names()` / `display_provider_names()` (2026-09-09)** are the derived counterpart to those three hand-written aggregates, and exist so the status sites never have to repeat the list. `all_provider_names()` is `tuple(f.name for f in dataclasses.fields(AllLimits))` — which providers exist. `display_provider_names()` filters that through a lazily-imported `dispatcher.policy_allows_provider(name, None)` — which of them are reachable. Measured against the live vault 2026-09-09: `('claude', 'codex', 'opencode')`. **Which of the two a caller wants follows from display vs. record**: the three human-facing sites take the filtered one, `heartbeat._append_capacity_log()` takes the unfiltered one because it writes the data analytics later parses (see the heartbeat entry above). gemini drops out because its 2026-08-15 retirement removed it from policy.yaml's `tool_providers`, so the display follows that decision instead of restating it in a fifth and sixth list. ## `quota_calibration.py` / `quota_state.py`

Calibrate a local `tokens_per_pct` quota model against `cclimits`, then expose a single-source-of-truth state file — so the orchestrator depends less on the undocumented, rate-limited `api.anthropic.com/api/oauth/usage` endpoint ([anthropics/claude-code#31637](https://github.com/anthropics/claude-code/issues/31637)).

### Phase 0 — calibration telemetry (`quota_calibration.py`)

Each successful `cclimits` poll in `_bg_refresh_loop` schedules (async, single-worker pool — never blocks the refresh loop) one CSV row per Claude window (`five_hour`, `seven_day`) to `logs/quota-calibration.csv`, pairing the real utilization-% with JSONL-derived token counts.

- **Window-aware aggregation:** `window_start = reset_at - window_size` from cclimits' `resets_in`; JSONL entries filtered on `timestamp >= window_start` (not a rolling "last N hours"), so a fresh block does not inherit the previous block's tokens. JSONL loaded once per poll (7d-sized + 10 %/6 h drift buffer), filtered per-window in memory.
- **Schema v2** (`schema_version` first column rejects mixed-version files): `schema_version, timestamp_utc, window, claude_plan, queue_idle_at_sample, cclimits_pct_used, cclimits_pct_remaining, reset_in_sec, window_start_utc, tokens_input, tokens_output, tokens_cache_creation, tokens_cache_creation_1h, tokens_cache_creation_5m, tokens_cache_read, tokens_inputoutput_only, tokens_weighted_billing, tokens_per_pct_io_only, tokens_per_pct_with_cc, tokens_per_pct_all, entries_count, models, flag_rolling_fallback, flag_low_pct, flag_cm_unavailable, note`.
- **Flags** (skip for ratio analysis): `flag_rolling_fallback` (cclimits `resets_in_sec=0`, synthetic start), `flag_low_pct` (`pct_used < 0.5%`, division noise — ratio columns left empty), `flag_cm_unavailable` (claude-monitor missing/broken — cclimits side still preserved).
- **Sample rate:** 5 min active / 10 min idle (`_BG_POLL_AVAILABLE_SEC` / `_BG_POLL_IDLE_SEC`); overlapping submissions dropped. Hard skip when Claude has any error string or no window data. Requires `claude-monitor>=3.0.0` (optional → `flag_cm_unavailable=true`).
- **Limitations:** single-machine (local JSONL ≠ cclimits' account-wide sum), single-orchestrator (CSV thread-safe, not process-safe — override `QUOTA_CALIBRATION_LOG_FILE` per instance), JSONL flush latency (active long tool calls briefly lag cclimits — `queue_idle_at_sample=false` rows), cache sub-tier mix.

**Result (2026-05-27, ~6 days, 558 usable samples, plan = max5):** `io_only` (input + output) won — 7d CV 6.9 % vs. `with_cc` 10.1 %, `all` 10.7 %. 5h noisier (best 21.6 %) but that is low-pct division noise — 5h `io_only` CV falls to 15–18 % in the ≥60 % band where gating matters, with a stable median. Both windows favour low/zero cache weight → cache tokens barely count against the rate limit. **Conservative low-percentile factors are plan- and workload-specific** (env-overridable, NOT universal): **5h ≈ 5400, 7d ≈ 75000** effective tokens per 1 %.

**Refuted 1h/5m tier-split:** the plan's fallback (split `cache_creation` into ephemeral 1h/5m tiers via direct JSONL parse if the lumped cache ratio was unstable) was built as a one-time analysis (`quota_calibration_backfill.py`, dedup key `(message.id, requestId)`, 0.00 % median deviation vs. claude-monitor) and rejected: even a grid-optimal weighting only reached 17.7 % CV on the 5h window (gate 15 %). Not wired into production; the `tokens_cache_creation_1h/5m` CSV columns stay empty.

### Phase 2 — live between-poll rebalancing (opt-in)

Closed-loop estimation against cclimits, flag-gated (default OFF — it changes capacity gating in normal operation; conservative factors lean toward over-gating, the safe side). Both parts only act when `ORCH_QUOTA_LIVE_ESTIMATE=true`.

- **(a) Live between-poll estimate:** `report_estimated_usage` accumulates each task's calibrated per-window usage into `_live_estimated_usage` (normal mode; the 429 path is unchanged). `get_limits()` / `get_cached_provider_pct` / `is_cached_provider_available` subtract it at serve time via `_apply_live_estimate` (recomputing per-window remaining + `available`), so back-to-back tasks see consumption immediately instead of a static cached value. Each successful poll re-anchors via `_reset_live_estimate()` (the fresh reading already reflects that consumption). The SoTH file is rewritten on each task (`_write_live_quota_state`) so the statusline reflects the live decrement. Lock order is always `_limits_cache_lock` → `_live_estimate_lock`.
- **(b) Auto-recalibration** (`ORCH_QUOTA_AUTO_RECALIBRATE=true`, requires (a)): once per day the bg loop calls `_maybe_recalibrate` → `quota_calibration.recalibrate_claude_factors(csv, defaults, min_samples, clamp, percentile)`, which schema-aware-parses the running CSV (sidesteps a stale header), filters flagged rows, takes the conservative `percentile`th (default P25) `io_only` tokens-per-pct per window, requires `≥ min_samples` (default 60) per window, clamps each factor to `[default/clamp, default*clamp]` (default 3×), and is all-or-nothing across the two Claude windows. On success it updates the live factors via `limits.set_calibrated_windows` (held in `_active_calibrated_windows` under `_active_calibration_lock`); otherwise the frozen defaults stay. Env: `ORCH_QUOTA_RECAL_MIN_SAMPLES`, `ORCH_QUOTA_RECAL_CLAMP`, `ORCH_QUOTA_RECAL_PERCENTILE`.

The first version used the module-local `_owning_provider_for_alias()`, which spans **all six** providers while the second-opinion phase consults only four alias maps: `#second_opinion:opencode_glm` resolved to `opencode` in the linter and to `None` at runtime, so a live queue line earned a `second_opinion_not_allowed` warning for a phase that is skipped under *every* policy — widening `review-loop:` in `policy.yaml` would have silenced the warning without ever enabling the second opinion, the exact error `#pass1:` is excluded for (found in review 2026-09-09, measured on `opencode_glm` and `gemini_flash`). A drift guard (`test_second_opinion_provider_cannot_drift_from_review_loops_own_mapping`) now pins the two to each other.
The `policy_missing` **message** describes the runtime: claude/codex/opencode keep running, a bare `#vibe`/`#openrouter` tag without explicit authorisation ends with `provider_not_allowed`. Until 2026-09-17 the forced-tag branch never consulted `_allows()` and the message had to say such a tag *runs*; `test_bare_uncapped_tag_under_a_missing_policy_is_reported_as_barred` (formerly `…_as_running`, flipped with the fix) pins the dispatcher behaviour and the linter ERROR together, and `test_missing_policy_warning_describes_the_fail_closed_forced_tag` pins the wording. Not covered: `dispatcher.policy_dead_end()` (an *untagged* task the policy leaves unroutable) and provider tags on `#parallel` subtasks — the same blind spot model tags already have.

Sorts findings by `(line_no, level)`. Zero LLM calls — pure validation, though the policy check does construct dispatcher's provider singletons; the import is lazy and any failure degrades to a `policy_check_failed` WARN rather than taking the run down.

## `tools/base_tool.py`

`BaseTool._runtime_deadline()` returns a monotonic deadline from `policy.get_engine().get_tool_contract(name).max_runtime_sec` (fallback `TOOL_DEFAULT_MAX_RUNTIME_SEC=3600`) — bounds the SUM of all phases/iterations so a high per-call `#timeout:` hard backstop cannot bind 10+ hours of wall-clock. `BaseTool._phase_cap(task_timeout, phase_default)` returns `min(task_timeout, phase_default)` (or `phase_default` when no task timeout) — a high task timeout is an upper deckel only and never raises a phase above its `TOOL_*_TIMEOUT_SEC` constant. All three iterative loop tools (review-loop, dev-loop, **test-loop**) check the deadline at each iteration start and bail with `error_code="tool_runtime_exceeded"` (partial output). The orchestrator tool-loop treats `tool_runtime_exceeded` as **terminal**: it finalizes the task with the partial result instead of falling back to the next provider or `mark_retry`'ing — both would restart the loop from iteration 1 with a FRESH deadline (3× the budget across providers, unbounded across polls), defeating the wall-clock bound.

`BaseTool` ABC + `_build_system_prompt(provider_name, memory_context, tool_name, cwd)` assembles system prompt with 4 memory layers ordered by stability for max prompt-cache reuse: (1) provider system prompt (SOUL+SAFETY, static), (2) curated MEMORY.md, (3) lessons (cwd-filtered, stable per tool+cwd), (4) daily log (grows during the day), (5) task-specific TF-IDF memory_context. **Lessons before Daily** is intentional — daily grows over the day and would otherwise break the prefix cache for tool+cwd reruns.

`ToolResult` carries the same four token fields as `RunResult`. `TokenCounter` helper (`.add(result)` / `.as_kwargs()`) aggregates tokens across phases — used by review-loop and dev-loop, other tools may adopt incrementally.

**`SessionContext`** helper (`SessionContext.create(provider, tool_name, cwd, cap=5)` + `.first_call_kwargs()` / `.resume_kwargs()` / `.bump()` / `.needs_rollover()` / `.rollover()`) manages CLI session lifecycle for tools that share conversation history across phases. Activates only when `provider.supports_sessions and config.CLAUDE_SESSION_ENABLED`; otherwise transparently returns empty kwargs (callers fall back to today's stateless pattern). Auto-registers UUIDs in the sidecar registry. All tool subclasses pass `tool_name=self.name, cwd=cwd` for CWD-filtered lesson injection.

**`ToolTracer`** helper (`ToolTracer.create(tool_name, cwd)` + `.emit(action, **details)`) writes one JSONL event per phase/iteration/subprocess to `{cwd}/.{tool_name}/traces/{uuid}.jsonl`. Silent no-op when `cwd is None` or directory creation fails — never breaks the tool. Suggested action vocabulary: `run_start`/`run_end`, `phase_start`/`phase_end`, `iteration_start`/`iteration_end`, `subprocess_call`/`subprocess_result`, `session_rollover`, `capacity_exhausted`. Open-ended `details` dict for tool-specific fields. Consumed by `analytics._parse_tool_traces()` for dashboard aggregation.

**`ActiveRunRegistry`** — zentraler Live-Index laufender Tool-Runs unter `logs/active_runs/<run_id>.json` (file-per-run für lock-free parallelen Zugriff). Wird automatisch über `ToolTracer.emit()` befüllt — Tool-Code muss nichts ändern, nur die emit-Vocabulary verwenden. ## `tools/review_loop.py`

`ReviewLoopTool` — iterative code review fixing **P1 + P2** (max 20 iterations). **P3 is non-blocking** (changed 2026-07-30): findings are split into `blocking_findings` / `deferred_p3`; the success gate is `no_findings or not blocking_findings`, only blocking findings reach the fix prompt, and the deferred P3 are appended once to the final output as an offer. `deferred_p3` is an ordered `dict[str, None]` **outside** the iteration loop — a per-round list dropped a round-1 P3 as soon as round 2 came back clean, i.e. exactly the case the "collected once at the end" promise exists for. Rationale: touching working code for cosmetics widens the diff without functional gain, and because each round re-reads the fresh diff, every P3 fix can surface new P3 — the loop would feed itself. `tools/dev_loop.py` had the split already (`blocking_findings` there gates `quality_ok`) and now accumulates + emits the same closing offer.

**Scope of the P3 exclusion:** it is a *prompt* guarantee, not a context guarantee. With `CLAUDE_SESSION_ENABLED=true` the review and fix calls share one conversation (`SessionContext` + `--resume`), so filtering `findings_text` removes P3 from the new prompt but not from the resumed history — the writing call can still see a P3 named in an earlier review. Closing that would mean a fresh session before every write call, forfeiting exactly the prompt-cache benefit session reuse exists for; declined deliberately. What holds in both modes: no P3 is ever *requested*, and the success gate counts only blocking findings, so a P3 can never keep the loop running. The same applies to `dev_loop.py`, where sessions span all phases.

The success gate is guarded against self-contradicting reviewer output by `_is_clean_output(text, findings)`: output carrying both `- [P2] …` and the `No P1/P2/P3 findings.` sentinel used to pass, because `_is_no_findings_output()` alone satisfied the left side of the `or` while a real blocking finding sat unfixed. The findings win now — the sentinel counts only when nothing parsed as a finding. `_is_no_findings_output()` stays the raw sentinel detector; both loops (and the second-opinion merge) call `_is_clean_output()`.

Infinite-loop detection via finding signature dedup — the signature is built from the **blocking** set, so a round in which only the P3 list shifted cannot read as "new findings" and defeat the no-progress detection; the drift-check counters and `previous_findings_count` use the blocking count for the same reason. Fix prompt is split into stable prefix (`_FIX_PROMPT_STABLE`, cached across iterations) + volatile suffix (`_FIX_PROMPT_VOLATILE` with iteration-specific findings + lessons hint at the end) — Anthropic prompt cache matches the longest identical prefix, so volatile content lives at the end. `_FIX_PROMPT_STABLE` carries `ORIGINAL TASK: {task}` (fixed 2026-09-04, mirrors `dev_loop.py`'s `_EXECUTION_PROMPT`/`_QUALITY_REVIEW_PROMPT`/`_RESOLUTION_REVIEW_PROMPT`): the scope-guard bullet below it ("Fix ONLY issues ... related to the original task") had nothing to check itself against before, since `CLAUDE_SESSION_ENABLED` is off by default and the fix call has no other channel to the task text. Placed in STABLE rather than VOLATILE deliberately — the task is invariant across a run's iterations, so it extends the cacheable prefix the same way `system_prompt` already does in front of it, whereas VOLATILE's `Iteration: {iteration}` line already breaks the cache match on every call regardless of what follows.

**Phase B sessions**: `SessionContext` shares conversation history across review→fix→review iterations with `cap=5` rollover; review prompt always reads `git diff` fresh, so a fresh-session continuation is seamless. Fallback on `session_missing` resets to a fresh UUID and retries once.

**Second-Opinion** (opt-in via `#second_opinion:<alias>` tag, e.g. `#second_opinion:or_glm`): in iteration 1 only, after the primary review, a non-agentic LLM (typically OpenRouter via `or_*` alias) receives `ORIGINAL TASK: {task}` (fixed 2026-09-04) plus the pre-loaded git diff + the primary's findings, and lists *additional* P1/P2/P3 issues. Without the task text this voice only ever saw "here's a diff, here's what reviewer A found" — an independent perspective that can extend reviewer A's frame but structurally cannot notice scope drift (work done past the task), which duplicates the primary reviewer's blind spot instead of covering it. No `system_prompt` prefix here, unlike the fix prompt — this call is a single stateless review, not part of the cached review→fix cycle. Resolved via `_resolve_second_opinion(alias)` which maps model aliases to their owning provider (`or_*` → openrouter, `claude_*` → claude, `vibe_*` → vibe, …) and resolves through `dispatcher.get_provider_for_tool(name, "review-loop")` — policy-aware, so an alias barred by `tool_providers` yields None and the phase is skipped instead of reaching a provider the policy bars (under the current `review-loop: [claude]` that makes `codex`/`vibe`/`or_*` inert here; `claude_*` still resolves). Bare provider names are accepted from `_SECOND_OPINION_BARE_PROVIDERS = {openrouter, claude, codex, vibe}` — Gemini is deliberately absent (retired as a reviewer, fallback executor only). `#second_opinion:` is the ONE path that honours every alias, because it carries its own regex and resolution instead of `MODEL_TAG_RE`. Extra findings are union-merged into the finding list (exact-string dedup) **before** the blocking/P3 split, so a second-opinion P1/P2 reaches the fix prompt while a second-opinion P3 only joins the deferred offer — a P3-only second opinion therefore does not reopen the loop (it sets `no_findings = False`, but the gate asks for blocking findings). Non-fatal skips: SO provider in cooldown, diff fetch fails, diff > `TOOL_RL_SECOND_OPINION_MAX_DIFF_CHARS` (30k), or `_resolve_second_opinion` returns None — primary findings continue alone. Fix phase stays on Claude (or whatever the primary provider is) — second-opinion is read-only. Timeout: `TOOL_RL_SECOND_OPINION_TIMEOUT_SEC` (10 min).

**Drift-Check (Goal-Adherence-Guard)**: Mini-LLM-Call zwischen Review und Fix, prüft ob die Findings noch zum Original-Task gehören oder die Iteration in unrelated Refactoring abgedriftet ist. Modi via `policy.yaml` `tool_phases.review-loop.drift_check_mode`: `auto` (default — Trigger ab iter≥3 mit wachsenden Findings, Halbzeit, oder iter≥5 als Sicherheitsnetz), `always` (jede Iteration), `skip`. Output strikt `ON_TOPIC: <reason>` oder `DRIFTED: <reason>` (via `_parse_drift_check`). Bei `DRIFTED` wird eine Refocus-Warning in den **nächsten** Fix-Prompt-Volatile-Block injiziert — Loop wird nicht abgebrochen. Drift-Call-Fehler sind non-fatal. Scope-Guard im `_FIX_PROMPT_STABLE` (immer aktiv, kein Cache-Bust): instruiert Fix-Agent off-topic Findings zu skippen und als `SKIPPED (off-topic): <finding>` zu markieren. Timeout: `TOOL_RL_DRIFT_CHECK_TIMEOUT_SEC` (2 min, Mini-Prompt ohne Codebase-Exploration).

## `tools/dev_loop.py`

`DevLoopTool` — Research+Plan → Execute → Quality-Review + Resolution-Review (`RESOLVED`/`PARTIAL`/`UNRESOLVED`) loop until both reviews pass (max 20 iterations).

**Phase 1 (Research) and Phase 1.5 (Plan) are merged into a single subprocess call** (`_RESEARCH_AND_PLAN_PROMPT` produces both sections; saves ~42 k cache_creation tokens vs. the prior two-call pattern). Skip-mode (`policy.tool_phases.dev-loop.plan_approval=skip`) falls back to research-only via `_RESEARCH_ONLY_PROMPT`. State persisted in `{cwd}/.dev-loop/<task-hash>/state.json` under phase `research_and_plan_done` (or `research_done` for skip-mode), enabling capacity-exhausted retry without re-running the merged phase.

**Plan approval (`plan_approval: approve`) is real and fail-closed since 2026-10-06.** Until then the switch was dead twice: `_get_plan_approval_mode()` imported a `policy.load_policy` that never existed (ImportError → always `auto`, so `approve` AND `skip` never took effect — `skip` works for the first time now), and the approval imported a `notifier.request_approval` that never existed either (ImportError → "Plan-Approval uebersprungen" → the run went on). The mode now comes from `get_engine().get_tool_phase("dev-loop", "plan_approval", "auto")`: missing file/section/key → `auto` (the default stays), a value outside `auto|approve|skip` or any read failure → `approve` with a warning. `_ask_plan_approval()` asks through the process-wide `policy.get_engine()` — dev-loop runs inside the orchestrator process, so this is the engine the TelegramListener answers — with the task (≤200 chars) plus the plan (≤1000 chars), `timeout_sec=_PLAN_APPROVAL_TIMEOUT_SEC` (= `POLICY_APPROVAL_TIMEOUT_SEC`, 600 s) and the cwd. Only the exact answer `approved` executes; `denied`/`skipped`/`timeout` end with `approval_denied`/`approval_skipped`/`approval_timeout`, any exception, a missing engine or an unknown answer with `approval_unavailable` — always `ToolResult(success=False, retryable=False, iterations=0)`, so the orchestrator stamps ❌ instead of re-planning and waiting another 600 s on every retry while Telegram is down. Every exit without approval calls `_clear_state()` first, so a rejected plan does not stay a cache entry. **The gate sits after BOTH Phase-1 branches**, not only after a fresh plan: the plan checkpoint is written before the question, so Ctrl+C or a crash during the wait — and every plan cached under `auto` or by the old dead code — would otherwise reach execution through the cache branch unasked. The checkpoint therefore carries `plan_approved` (written by `_record_plan_approval()` only for the plan text that was shown, carried into every park checkpoint); a cached plan without it is asked for again, an approved and capacity-parked run resumes without a second question. `_PLAN_APPROVAL_LOCK` serialises the question across threads: `#parallel` runs CWD groups in parallel, and the engine has ONE pending slot that `/approve` answers blindly. Limits: the mark lives in a file the provider can write (same trust level as the worktree-gate proof), and a late answer to a timed-out request still lands on whatever request is pending next (engine-wide, request IDs would be needed). Tests: `tests/test_dev_loop_plan_approval.py` (only `notifier._send` faked).

**Output is keyed by task, not by cwd (2026-09-09).** `_run_dir(cwd, task_hash)` returns `{cwd}/.dev-loop/<task-hash>/` and every artefact goes there — `research-and-plan.md`, `round-00N.md`, `summary.md`, `state.json`. `_task_hash()` (sha256[:8] of the task text) existed from the start and was written *inside* `state.json`, but never reached the path, so two dev-loop tasks in one repository overwrote each other's files and the iteration counter restarted per run. The parent `DEV_LOOP_DIR = ".dev-loop"` is deliberately unchanged rather than renamed to `.dev-loop-<hash>`: `ToolTracer.create()` derives `{cwd}/.<tool_name>/traces/` from the TOOL NAME and `analytics._parse_tool_traces()` globs `**/.*/traces/*.jsonl`, so renaming the parent would move every trace file and silently change tool attribution — nesting leaves both untouched. **Altbestand: nothing is migrated, moved or deleted.** Pre-2026-09-09 artefacts stay directly under `.dev-loop/`; `_load_state()` checks the per-task path first and then falls back to the legacy shared `.dev-loop/state.json`, so a run interrupted *by* the upgrade still resumes — both paths validate `task_hash` and `tool`, so another task's state is never consumed. `_clear_state(cwd, task_hash)` removes the per-task file unconditionally and the legacy one **only when its `task_hash` matches**, because that location is shared by definition and deleting it blindly would destroy a different task's resume point. Nothing prunes either location (ROADMAP); editing a task's text starts a new subdirectory rather than continuing the old one.

**An unusable state file is treated exactly like a missing one** (`_read_state_file()`), and the guard has to be wide because the damaging call site is `_clear_state()`, which runs immediately before dev-loop's success return — an exception there converts a finished run (plan written, reviews passed, work done) into a reported failure. Three shapes are reachable. Valid json that is not an object (`null`, `[]`, `"x"`, `5`) parses fine and then raises `AttributeError` on `.get`, hence the `isinstance` check. A file cut inside a multi-byte character raises `UnicodeDecodeError`, which is **not** a `json.JSONDecodeError` — and that is the likeliest shape, because `_save_state()` writes with `ensure_ascii=False` and truncate-then-write, so a run killed mid-write (the watchdog's `taskkill /F /T`, a crash, a full disk) leaves the file ending part-way through an em dash or an umlaut, both routine in plan text. Malformed json and IO errors are the third. The clause is therefore `except (OSError, ValueError)` — `ValueError` is the common base of the two decoders, so no decoder is named and none can be forgotten. An unattributable legacy file is left on disk rather than deleted.

**Phase B sessions**: `SessionContext` shares conversation history across all phases when enabled, with `cap=5` rollover (fresh UUID after every 5 iterations to bound conversation length — explicit findings re-injection in `review_context` keeps the model in sync across the boundary). Fallback on `error="session_missing"` (e.g. cleanup deleted JSONL between calls): rollover + retry once with the same prompt.

Registered as `#tool:dev-loop`.

## `ci_watcher.py`

P4 CI-Failure-Watcher — module-level `sweep_once(repos, *, cooldown_hours, list_failed_runs_fn, append_task_fn) → summary` polled from the `check-ci-failures` heartbeat handler.

- Repo whitelist from `CI_WATCHER_REPOS` env var (semicolon-separated `owner/name`). Empty list disables the handler entirely (`_check_ci_failures` returns `None` immediately, no gh call).
- Dedup is per-`(repo, headSha)` — multiple failed checks on the same commit produce **one** queue item. Per-SHA marker persists in `logs/ci-watcher-state.json`.
- Cooldown of `CI_WATCHER_QUEUE_COOLDOWN_HOURS` (default 2h) blocks re-queueing the same SHA even if the state file gets reset.
- Queue line format: `CI failure (<repo>@<branch>, <sha7>): <title80> [cwd:<local>] #tool:dev-loop`. `CI_WATCHER_REPO_PATHS` env var (`owner/repo=local/path;...`) optionally maps repos to local clones so the queue item carries a usable `cwd:`. Unmapped repos get a queue line without `cwd:` — user must edit before it runs.
- Heartbeat handler returns `None` (no Telegram noise) when nothing was queued AND no gh errors occurred.

## `parallel_runner.py`

**Join cap (2026-10-06):** `_group_join_timeout_sec()` is the sum of the subtask timeouts + 120 s, plus, for a group with at least one subtask in `_APPROVAL_GATED_TOOLS` (`dev-loop`), `(questions_in_call + 1) × POLICY_APPROVAL_TIMEOUT_SEC` — `run_parallel()` counts the approval questions of ALL started groups, because `_PLAN_APPROVAL_LOCK` serialises them across groups and one group can queue behind every other one (K7; the first version added one foreign question per group only). A dev-loop subtask waits for the Telegram plan answer on top of its own timeout, and a cap without that slack gave up the join mid-wait, booked the subtask as failed and left a late `/approve` to run the plan in the abandoned daemon thread. Added regardless of the live mode. Not closed: nothing stops a thread abandoned for another reason (a real hang) from running after a late approval.

Existing parallel sub-agent runner extended with **worktree-isolation helpers** (P1). When the parent task carries `#worktree`, `run_parallel()`:

1. Pre-flights every CWD group: `_is_clean_git_repo(base_cwd) → (ok, reason)` runs `git rev-parse --git-dir` + `git status --porcelain`. Dirty trees / non-git dirs short-circuit the whole group with `provider_name="worktree"` failed results before any subtask spawns.
2. `_create_worktree(parent_cwd, worktree_id) → (path, err)` runs `git worktree add --detach <parent>/.worktrees/<id> HEAD`. `worktree_id = "parallel-" + sha1(parent_task|group_key|idx)[:8]` — short to fit Windows' 260-char `MAX_PATH` when nested deep.
3. Each subtask in the group has its `SubTask.cwd` rewritten to the worktree path before thread spawn.
4. `_remove_worktree(parent_cwd, wt_path)` runs `git worktree remove --force <path>` only when **all** subtasks of the group succeeded AND `#keep-worktree` is absent. On failure the worktree is **retained** and the path is appended to every failed subtask's `error` string (`... [worktree retained: <path>]`) for user inspection.

`PARALLEL_WORKTREE_ROOT` constant in `config.py` controls the subdir name (default `.worktrees`). Doctor check `check_worktrees()` scans `ALLOWED_CWD_ROOTS` for orphans and offers `git worktree prune` + remove via `--fix`.
