## Project

Autonomous task orchestrator routing work across Claude Code and Codex CLI, plus opt-in providers that never enter the fallback chain: OpenRouter (HTTP), Mistral Vibe (reviewer-only) and opencode CLI (tag-activated third external voice, Stufe 2 — a ZDR-guaranteed path for customer code, capped by its own OpenRouter key rather than uncapped like the other two). Gemini (HTTP API or legacy CLI) is still implemented but retired from every active path (2026-08-15). Tasks come from an Obsidian vault Markdown queue (`99_System/AI/agent-queue.md`). Pure Python stdlib + pyyaml, Windows-first.

## Architecture

**Execution flow**: Queue read → provider selection (fallback chain) → profile loading → policy check → skill gating → memory context injection → prompt building → provider execution → result persistence → heartbeat.

**Module map** (details in [`docs/architecture/components.md`](docs/architecture/components.md)):

### Core orchestration
- **`orchestrator.py`** — Main loop (`run_once`/`run_watch`), prompt building, heartbeat thread, blocked-task handling
- **`dispatcher.py`** — Provider selection (Claude → Codex fallback; **Gemini left `_PRIORITY` 2026-08-15** — IneligibleTierError + data protection. The provider stays registered, so `#gemini*` tags and `get_provider_by_name` still resolve; nothing routes there by default), cooldowns, model-alias routing; `_NO_FALLBACK_PROVIDERS = {"vibe", "opencode"}` (renamed 2026-09-04 from `_REVIEWER_ONLY` when opencode joined) guard so an unregistered vibe/opencode tag parks the task instead of degrading to another provider — two different reasons, one mechanism: vibe is blast radius (non-writing reviewer → writing executor), opencode is tag intent (the tag itself asks to avoid Claude quota, or for customer code the only ZDR path — a silent fallback would defeat it). **Policy gate:** `get_provider_by_name()` is the policy-BLIND registry lookup — tool code must use `get_provider_for_tool(name, tool)` / `policy_provider_lookup(tool)`, and `forced_provider_policy_violation()` lets the orchestrator tell "policy said no" apart from "no capacity" (both surface as `select_provider() → None`, but only the latter is worth waiting for)
- **`queue_manager.py`** — Obsidian MD queue parser, sidecar `.lock`, regex metadata, `#needs:`/`#id:` two-pass deps, subtask-aware mutations; P1 `#worktree`/`#keep-worktree` tags for parallel isolation; `#no-commit` (2026-09-10, opts one line out of the per-task auto-commit — same boundary shape as `#allow-dirty`, and like it a *bare* tag: `#no-commit-later` matches nothing, and a trailing comma breaks the right-hand boundary, which is repo-wide behaviour for every tag here); `#verify:<script>` post-task outcome check (unquoted path bounded by whitespace AND `#` — without the `#` bound adjoining tag text lands inside the script path, the lookup fails forever, and fail-closed turns that into a permanent alarm on every *successful* run); `collect_file_context()` returns context blocks WITHOUT the task text so `_build_prompt` can place the instruction last (see below). **Das Budget teilen sich nur die Refs, die sich wirklich aufloesen und lesen lassen** (gefixt 2026-08-28): der Divisor lief vorher ueber ALLE erkannten Referenzen, sodass ein Datums-Platzhalter oder ein `[[Projekt]]` aus erklaerendem Fliesstext einen vollen Anteil beanspruchte und ungenutzt verfallen liess — gemessen am vault-gardener-Task bekam die einzige echte Datei 1875 statt 7500 Zeichen. Chosen over rejecting the two values, because `_resolve_pass2_provider()` already routes an arbitrary provider name through `policy_allows_provider()`/`get_provider_by_name()`; the regex was the only thing standing between a valid tag and that existing path. **`PROVIDER_TAG_RE` is likewise derived from `_PROVIDER_TAG_MAP`** (fixed 2026-09-04, same pattern again): the hand-copied version only ever listed `claude`/`gemini`/`codex`, so a blank `#vibe` or `#openrouter` survived `strip_metadata_tags()` as literal prompt text instead of being stripped as routing metadata. **Now uses the same two boundaries as `MODEL_TAG_RE`, not `\b`** (same-day follow-up fix, found while reproducing the derivation): the old `\b`-only version had no LEFT boundary at all, so `Implement C#vibe bridge` stripped to `Implement C bridge` and `Besuche https://x/#openrouter heute` lost the URL fragment — text `has_explicit_provider_tag()` never treated as a tag in the first place, because its own `_TAG_RE_BY_PROVIDER` already required `(?<!\S)`. - **`scripts/safety_hook.py`** — Claude Code `PreToolUse` hook, hard-deny via `SAFETY_DENY_PATTERNS`. **The output shape decides whether it blocks at all:** Claude Code honours `decision: "block"` (legacy) and `hookSpecificOutput.permissionDecision: "deny"` (modern). Registered globally in `~/.claude/settings.json` (PreToolUse → `Bash`), i.e. it also applies to interactive sessions, not just orchestrator runs. **Command-start boundary (`config._CMD_START`)** — a git write pattern only counts where a command actually *starts*: line start, after `;`/`&`/`|`/newline, after `(` or a backtick, after a shell interpreter's `-c`/`-Command` argument, and (2026-08-15) after the command-taking builtins `eval`/`exec`, which were the same hole as `bash -c` in different syntax. ## Phase B Feature Flag — `CLAUDE_SESSION_ENABLED`

Default **OFF**. Opt-in via `.env`. When enabled, Claude tools share CLI session UUIDs across phases (`--session-id`/`--resume`) for ~30-50 % token savings. Rollback by setting `CLAUDE_SESSION_ENABLED=false` and restart. Dieselbe Lücke im `#parallel`-Parent (`except Exception` trug nur `str(e)`) ist mit einem `_log.exception` geschlossen; die Subtask-Seite loggte schon korrekt. `logging_setup.install_thread_excepthook()` deckt sterbende Threads ab — **zählt aber nie**, ein toter Thread startet den Prozess nicht neu. (2) Der Zähler ist der **vorhandene** `<!-- hang: N -->`, nicht ein zweiter Marker und kein Sidecar-State-File: ein zweiter Marker spaltet den einzigen persistenten Zustand der Queue auf zwei Parser, die jede Rewrite-Stelle synchron halten muss, und beide Varianten würden das unbeaufsichtigte Budget von 3 toten Versuchen auf 3+N **anheben** — dieselbe Abwägung wie 2026-08-15. Ein Absturz ist also die **dritte** Art erfolgloser Versuch neben `hang` und `format_error`, deshalb heißt die Meldung jetzt „Hang/Format-Fehler/Absturz zusammen gezählt". Über `MAX_HANG_RETRIES` hinaus wird der Task als `- [x] … ❌ …` quarantäniert (raus aus `OPEN_TASK_RE`, erfüllt kein `#needs:`, wandert nach 48 h ins Erledigt-File, umkehrbar über `/retry`). **Zugeordnet wird im sterbenden Prozess**, über ein flüchtiges Modul-Register (`_InFlightTask`, Vorbild `shutdown.py`), das `run_once` **nach** der Blocked-Prüfung armiert (unmittelbar vor dem Profil-Load) und an drei Stellen räumt: am **Anfang** jeder Iteration, nach der Schleife, und nach jedem **armierenden** `run_once`-Aufruf — der `--dry-run`-Aufruf armiert nie. Am Anfang der Iteration statt an ihrem Ende, weil der `#tool:`- und der `#parallel`-Zweig den Schleifenkörper per `continue` verlassen und ein Ende dort nie erreichen; sonst bliebe der vorige Task über ~30 ungeschützte Zeilen armiert — **und zusätzlich in beiden `_checked`-Wrappern, sobald eine Finalisierung persistiert ist**. Letzteres kam aus Review-Runde 2 und war ein gemessener Defekt: für einen normalen Task ist eine späte Belastung folgenlos (`[x]`-Zeile, `mark_retry` findet nichts), aber `_completion_replacement()` **stempelt eine `#every:`-Zeile nicht, sondern plant sie neu** — sie ist also wieder offen, und die Belastung greift: ein erfolgreich gelaufener Daily-Task kam 5 Minuten später erneut dran und trug einen Fehlversuch. Ebenfalls aus Runde 2 und der schwerere Fund: die Quarantäne wurde **hinter** `append_log` und `notify_error` geschrieben — wirft eines von beiden (ein Telegram-Roundtrip mit `print`-Fallback auf dem kaputten stdout eines fensterlosen `--watch`), wird sie nie geschrieben, der Zähler steht, und der unbegrenzte Loop läuft weiter. Der Queue-Write steht jetzt **vor** jeder Meldung; alle **neun** neuen Gates sind per Mutationsprobe belegt — jedes einzeln kaputt gemacht, Test rot, Original wiederhergestellt. Das ist kein Ritual: **vier** Gates waren in ihrer ersten Fassung **trivial grün** — der `dry_run`-Guard (vom internen Review per Mutationsprobe nachgewiesen), zwei der drei Codex-Gates (fehlender Hook-Aufruf, falsch gewählte Mutationsstelle) und der `#parallel`-Subtask-Test, der am falschen Modul patchte und deshalb aus dem falschen Grund bestand — dazu ein **fünfter** Fall anderer Art: der Fix für das ungeschützte Logging in `main()` ging ganz ohne Gate raus und fiel erst auf, als alle Mutationen am Stück liefen und genau eine keinen Test rot machte — bei dieser Fehlerklasse ist ein grüner Test ohne Gegenprobe kein Beleg. **Um die Task-Iteration liegt bewusst kein `try/finally`**: es würde auf dem Absturzpfad genau den Kontext löschen, den `main()` zum Zuordnen braucht. (Nicht zu verwechseln mit dem `try/finally` **in** `main()`, das seit dem externen Pass den Exitcode garantiert — das ist eine andere Stelle mit dem gegenteiligen Zweck.) Der Gewinn: Ctrl+C, `taskkill`, Windows-Update und Stromausfall sind **strukturell** nicht zählbar statt nur heuristisch gefiltert (1 von 97 Prozessenden jener Nacht war ein User-Kill, den ein Breadcrumb-File mitgezählt hätte). **Der externe Pass (Stufe 2: Codex + Mistral) hat vier weitere Löcher gefunden**, alle gefixt: `sys.exit(1)` hing hinter ungeschütztem Logging und einer Queue-Operation — jetzt in einem `finally`, sonst hätte der Prozess auf dem Default-Excepthook der ursprünglichen Exception geendet, mit anderem Exitcode und doppeltem Traceback; `_charge_process_crash` fing nur `Exception`, obwohl der Docstring „never raises" verspricht — jetzt `BaseException`, und der gesamte Rumpf liegt im Schutz; `logging_setup`s Thread-Hook prüfte `args.exc_type is SystemExit` statt `issubclass`, hätte also einen geordneten Thread-Stopp über eine Unterklasse als CRITICAL protokolliert; und der `#parallel`-**Subtask**-Pfad war zwar dokumentiert, aber von keinem Test wirklich ausgeführt — jetzt läuft ein echter Subtask-Absturz durch `parallel_runner.run_parallel()` und belegt, dass er als `SubTaskResult(success=False)` endet statt den Prozess zu erreichen. **Fünf Grenzen, benannt statt entdeckt:** ein harter Prozesstod (OOM, Segfault in einer C-Extension) wird gar nicht gezählt und läuft weiter unbegrenzt gegen dieselbe Zeile; die ~30 Zeilen **vor** dem Setzpunkt (Task-Text, `replay.new_run_id()`, `_RunSpan`, der `#needs:`-Zweig) laufen unarmiert, ein Absturz dort wird also niemandem angerechnet — früher zu armieren würde das schließen, aber auch Tasks armieren, die sich als **blockiert** herausstellen und nie laufen; die Prioritätsregel des Auftrags entscheidet das, weil eine Fehlbelastung still einen echten Task überspringt, eine ausgelassene Belastung dagegen nur den Status quo lässt; eine umgebungsbedingte Exception *innerhalb* der Task-Iteration wird dem laufenden Task zugerechnet, bei task-unabhängiger Ursache also dem **ersten** Task der Queue — und nach dessen Quarantäne dem jeweils nächsten, die Quarantäne wandert also durch die Queue (gedämpft durch Budget 3, lautes CRITICAL+Traceback, ❌ das keine Abhängigkeit freigibt, und Umkehrbarkeit); und ein `#every:`-Task ist nicht quarantänierbar, weil `_completion_replacement()` ihn neu plant — dieselbe geerbte Grenze wie beim Hang-Block-Pfad, aber die Meldung sagt es jetzt auch (die erste Fassung meldete per Telegram „wird nicht erneut gestartet“, was für eine wiederkehrende Zeile gemessen falsch ist). **Codex meldete das im externen Pass als P1** („kann über beliebig viele Termine weiter abstürzen“) — nachgemessen ist es milder: die Zeile wandert auf den **nächsten Slot** (`<!-- retry: 2026-09-11 07:00 -->`) und ist nicht sofort wieder fällig, pro Termin also 3 Abstürze (~20 min) plus eine Telegram-Meldung, kein unbegrenzter Loop. Über Tage wiederholt es sich. **Vom User bewusst so gelassen**, mit dem tragenden Argument: der bestehende Hang-Block-Pfad verhält sich bei `#every:` **identisch** — eine Sonderregel nur für Abstürze würde Hang und Absturz bei wiederkehrenden Tasks auseinanderlaufen lassen, für einen Fall mit null gemessenen Vorkommen. Wer das ändert, muss beide Pfade zusammen ändern; und **der `#parallel`-Elternzweig wird von diesem Deckel gar nicht erreicht**. Zwei verschiedene Gründe, die man leicht verwechselt: ein **Subtask**-Absturz erreicht den Prozess nie, weil `parallel_runner._run_group` jede Exception aus `_execute_tool_task` schon eine Ebene tiefer abfängt und in ein gescheitertes `SubTaskResult` verwandelt — der im Auftrag zitierte blinde Fleck des Worktree-Gates existiert hier also gar nicht, die Armierung ist für diesen Pfad nur Tiefenverteidigung. Der offene Fall ist der andere: ein Fehler in `run_parallel()`s eigenem Orchestrierungscode (Worktree-Setup, Aggregation) läuft in ein **bestehendes** `except Exception`, das über `_mark_retry_checked(..., "parallel", ...)` **ohne** `hang_count` requeued, den Zähler also stehen lässt: unbegrenzte Wiederholung alle 10 Minuten, nie quarantäniert. Der Prozess stirbt dabei nicht, es ist also strukturell kein Prozess-Absturz und fällt unter die allgemeine Regel weiter unten (`<!-- hang: N -->` ist der EINZIGE persistente Task-Retry-Zähler, jeder andere `error_code` requeut poll-übergreifend unbegrenzt). Im Resolution-Review vom 2026-09-10 gefunden, gemessene Exposition **0 Vorkommen in 131 Replay-Records seit dem 2026-08-11**, und vom User bewusst **offen gelassen**: der Fix wäre kein Einzeiler, sondern ein vierter urteilender Pfad samt vierter Meldungsvariante, und damit genau der „allgemeine Retry-/Quarantäne-Mechanismus für andere Fehlerklassen", den der Auftrag als KÜR ausgeschlossen hatte . Eine editierte Queue-Zeile wird **nicht** belastet (`mark_retry` findet den Text nicht → WARNING, nichts gezählt) — die konservative Richtung. **Die Quarantäne meldet per Telegram** (`notify_error`), der Requeue-Zweig bewusst nicht — er ist nicht terminal, der Task kommt von allein wieder. Nötig war das, weil die Quarantäne der einzige Zustand ist, den man nicht durch Warten entdeckt: die Zeile ist aus der offenen Queue verschwunden, und für eine abgestürzte Iteration wird **kein Replay-Record** geschrieben (`_span` wird nie emittiert), also sehen `runs.jsonl`, Taxonomie, Dashboard und Status-Recap davon nichts. Die erste Fassung behauptete stattdessen, `queue_healing` melde es nach 24 h — falsch: `detect_candidates()` iteriert `read_queue_items()`, und eine `- [x]`-Zeile ist dort gar nicht enthalten; Healing sieht nur einen dadurch blockierten *abhängigen* Task, und nur wenn es einen gibt. `docs/architecture/patterns.md` trägt die Zähler-Regel (`components.md` lag beim Bau unter fremdem WIP und ist hier nicht der richtige Ort).

## Safety Rules (enforced in code)

- **Hard deny**: `scripts/safety_hook.py` (Claude Code `PreToolUse` hook, works even with `--dangerously-skip-permissions`)
- **Soft deny**: `SAFETY_RULES` injected into the non-Claude provider prompts (`config.SYSTEM_PROMPTS`) — they have no hook system. **The asymmetry resolved on 2026-08-17:** `SAFETY_RULES` says *"NEVER push to remote unless the task explicitly says to"* and says **nothing about `git commit`** — and since the hook stopped denying commits, the two layers finally agree. Consequence to be aware of: **nothing in hook or prompt restricts `git commit` any more.** If unattended runs should be kept out of git state, `policy.yaml`'s `approve:` entries are the only remaining lever. **Since 2026-09-10 the orchestrator writes git state itself** (`git_commit.py`, one `orch/*` branch per successful task — see Key Patterns), which is deliberate and is the reason the executor prompt keeps saying `Do NOT commit`: the provider must not commit, because the dev-loop reviewers judge the uncommitted working-tree diff, so the orchestrator does it *after* the loop instead. That also makes the feature work for Codex and opencode, which cannot commit at all. Levers to switch it off: `GIT_AUTO_COMMIT=false` globally, `#no-commit` per queue line.
- **Blocked categories**: `rm -rf`, `git push --force`, `git reset --hard`, `git clean -f`, `DROP/TRUNCATE TABLE`, `DELETE FROM` without WHERE, `format`/`mkfs`/`diskpart`, fork bombs, raw disk writes, credential exfiltration, Windows `del /s`/`rd /s /q`/`Remove-Item -Recurse -Force`
- **Git state (revised 2026-08-17)**: `git push` is hard-denied; **`git commit` is not** — it was, from 2026-08-15 until 2026-08-17. The original rule was meant to keep unattended runs from changing git state, but nothing in the hook ever tested for "unattended": it is registered for *every* Bash call, so it blocked interactive sessions exactly as hard, including ones where the user had just asked for the commit, with no way to override it from inside the session. Dropped for that reason, keeping the irreversible half — a commit is local and revertible (`git reset`), a push leaves the machine and cannot be taken back. Built from `config._git_pattern()` (the hook's import-failure fallback mirrors it as `_fallback_git_pattern()` in `scripts/safety_hook.py`; `_git_subcommand_pattern()` never existed — corrected 2026-09-05) so `git -C <path> push` / `git -c k=v push` / `git --no-pager push` match while read-only commands containing the word (`git log --grep=push`, `git show`, `git rev-parse`) do not. Two known limits: the hook only covers Claude (Codex is fenced by its own sandbox — see below), and the match runs on the raw command line, so a command that merely *quotes* the text `git push` is blocked too.
- **opencode writes with neither a hook nor a sandbox (2026-09-04)**: `providers/opencode.py` runs `--agent extern-dev` whenever `read_only` is not set — and the plain-task path calls `provider.run(prompt, cwd=cwd, timeout=timeout)` without it, so **every ordinary `#opencode` task runs with the writing agent**. The Claude hook does not cover it (different CLI), and there is no Codex-style `--sandbox` flag. The only real fence is the machine-local `~/.config/opencode/opencode.json`: its `extern-dev` block carries `bash: deny`, `webfetch`/`websearch: deny` and `external_directory: deny` (measured 2026-09-04 — `external_directory` is the LAST matching permission rule, which is also why an out-of-`--dir` file can never be re-read and why the prompt cap has to fail loudly instead of truncating). That file is deliberately never written by this repo, and `doctor.check_opencode_cli()` validates only the **ZDR half** of it (aliases, `small_model`, spending cap) — the permission blocks are not checked at all. So the guarantee for the opencode path is exactly as strong as that user-level config, the same way `experimental_windows_sandbox = true` is the whole guarantee for Codex.
- **Codex git writes**: `providers/codex.py` runs `--sandbox workspace-write`, which on Windows denies writes inside `.git/` (`git add`/`commit`/`remote add` fail with "Permission denied" on `.git/index.lock`, verified 2026-08-15) — but only while `experimental_windows_sandbox = true` in `~/.codex/config.toml`. That user-level flag is the whole guarantee for the Codex path.
- **Pre-task git snapshot lives in its own ref namespace (2026-09-03)**: `_git_snapshot()` writes the `git stash create` commit to `refs/orchestrator-backup/<timestamp>` via `git update-ref` (empty `oldvalue` = create-only, `_2` suffix on a same-second collision) — **never to `refs/stash`**, which is the user's own list and where the old `git stash store` piled up 11 unreclaimed entries because nothing in the repo ever ran `stash drop`/`clear`/`pop`. `_prune_snapshot_refs()` caps the namespace on each write: `age >= GIT_SNAPSHOT_PROTECT_DAYS (14) AND (age > GIT_SNAPSHOT_MAX_AGE_DAYS (30) OR outside the newest GIT_SNAPSHOT_MAX_COUNT (50))`. The protect window is a **veto** over both caps, not a third equal test. **Begründung neu gefasst 2026-09-11**, als der Per-Task-Auto-Commit landete: die alte Fassung („night tasks deliberately do not commit, so the snapshot is the only undo") war damit an beiden Hälften falsch. Die Schlussfolgerung überlebt, der Grund ist ein anderer — Snapshot und `orch/*`-Branch decken **Verschiedenes** ab. Der Branch trägt das **Ergebnis** des Laufs für die Pfade, die der Commit genommen hat; der Snapshot trägt den Zustand **davor**, Index eingeschlossen, für alles, was der Commit bewusst liegen ließ (fremd gestaged, beim Start schon schmutzig, Konflikt, Rename) — plus jeden fehlgeschlagenen Lauf und jeden übersprungenen Commit, wo überhaupt kein Branch existiert. Das sind genau die Fälle, in denen fremde Arbeit im Spiel ist, das Undo ist dort also weiterhin einmalig. Umgekehrt deckt der Branch etwas ab, das der Snapshot nie konnte: `git stash create` erfasst **keine** untracked Dateien, der Commit schon. Deshalb wird auf Task-Erfolg weiterhin nichts gelöscht; der count cap kann in einem Repo mit hoher Änderungsrate ausgehungert werden (bewusst). Scoped by a `startswith(GIT_SNAPSHOT_REF_PREFIX)` re-check per ref, so branches, tags, `refs/stash` and the adjacent `refs/orchestrator-backup-sibling/` are out of reach; never raises. Ref name + `git stash apply <ref>` go to **both** `print` and `logger` — `git stash list` no longer shows the snapshot, and `run_orchestrator.ps1` starts `--watch` without stdout redirection. **Alterung laeuft ueber `committerdate`, nicht ueber den Eintritt in den Namensraum** — ein von Hand hereingeschobener Ref (die 11 Maerz-Archive) behaelt das alte Commit-Datum und faellt beim allerersten Prune; die Ref-*Namen* tragen dieselben alten Timestamps, Namens-Alterung hilft also nicht. Deshalb: jede Loeschung mit Name **und** Sha ins Log (bis `git gc` ueber `git stash apply <sha>` erreichbar), und **mehr als ein Ref in einem Durchgang** geht auf `WARNING` statt `INFO` — ein *routinemaessiger* Prune raeumt hoechstens einen Ref ab, mehrere auf einmal sind die Massenverlust-Form und duerfen im unbeaufsichtigten 03:00-Lauf nicht wie Housekeeping aussehen
