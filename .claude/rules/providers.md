# Provider-Implementierungen

Ausgelagert aus CLAUDE.md am 2026-09-21; laedt automatisch bei Zugriff auf providers/*.py.

- **`base.py`** — `BaseProvider` ABC, per-provider `_lock`, `threading.local()` for forced model, `RunResult` with 4 token fields, `supports_sessions` capability flag
- **`process_runner.py`** — Liveness-/Hang-Watchdog: `Popen` + 2 daemon-Reader-Threads (stdout/stderr gleichzeitig, sonst Pipe-Buffer-Deadlock), `idle_timeout` (Hang) + `hard_timeout` (Backstop), Tree-Kill (Windows `taskkill /F /T` doppelt, POSIX `killpg` SIGTERM→SIGKILL). Claude tool-aware (`liveness_lines=True`: laufender `tool_use` pausiert idle-Timer via `_Liveness`), Gemini/Codex byte-only. `run_with_watchdog` ersetzt `subprocess.run` in allen 3 Providern (DRY). Raise `TimeoutExpired` mit `timeout_kind` ("idle"|"hard"). **stdin-Zustellung wird verifiziert** (`_StdinDelivery`, fail-closed): gepufferter `TextIOWrapper` → ein fehlgeschlagener Tail-Flush schneidet das Prompt-ENDE ab, wo `_build_prompt` den Task-Text platziert → CLI antwortet auf den Kontext-Rest, exit 0, sah früher wie Erfolg aus (5× beobachtet, 3 Tage Daten-Lücke). Fehler → `WatchdogResult.stdin_error` → Provider liefern bare code `stdin_incomplete`, aber nur an zwei Stellen: **im Erfolgszweig** und **als letzter Fallback bei `rc == 0`**. Nie vorab — ein früh sterbendes Kind zerreißt die Pipe ebenfalls, ein Vorab-Check würde also `rate_limit`/`session_missing` maskieren; umgekehrt würde der Fallback bei `rc != 0` gewöhnliche CLI-Abstürze einsammeln. Bei `rc != 0` gewinnt der echte Fehler, die Diagnose wird an `output` angehängt. Im Orchestrator **bewusst nicht sonderbehandelt** (generischer Pfad = Cooldown + Rotation, bounded); nur in der `_run_with_retry`-Abbruchliste. **Blind-Spot + Fix (2026-07-24):** diese Detektion prüft nur die Schreibseite — passt der (≤64-KB-)Tail eines großen Prompts noch in den Kernel-Puffer, nachdem das Kind zu lesen aufhört, gelingen `write/flush/close` und `stdin_error` bleibt None → der stille Ausfall kehrte zurück (morning-brief). Der Claude-Provider stellt den Prompt daher jetzt über eine **Temp-Datei als stdin** zu (`stdin_via_file=True`, `_write_temp_prompt`: deterministisches EOF am Dateiende, kein Feeder-Race) + `shell=False`; der Feeder-/Detektions-Pfad bleibt Default für Codex/Vibe/Gemini
- **`claude.py`** — `--output-format stream-json --verbose` (NDJSON-Liveness-Events), NDJSON-Parser `_extract_result_event` (letztes `type==result`), Token-Feld-Parity erhalten, rate_limit/session-Keyword-Detektion auf ROH-stdout, `--exclude-dynamic-system-prompt-sections` for cache stability, session-id/resume support, `supports_sessions=True`; idle-Kill → `error="hang"`, hard → `error="timeout"`
- **`gemini.py`** — **dual-mode** (consumer Gemini CLI shut down 2026-06-18). `GEMINI_API_KEY` set → HTTP REST API via `urllib` (`generateContent`, stdlib, like `openrouter.py`); real tokens from `usageMetadata` (thinking tokens folded into output), 429→`rate_limit`+cooldown, finishReason/promptFeedback → `model_refusal`. No key → legacy `gemini` CLI (`--yolo`/`--approval-mode default`/`--model`, byte-only Liveness) for Standard/Enterprise users. HTTP mode availability is cooldown-driven (`dispatcher._limits_ok` + `limits` bypass cclimits when key set). **Retired 2026-08-15** (IneligibleTierError + data protection): out of `_PRIORITY`, out of `policy.yaml`'s `tool_providers`, and `GEMINI_API_KEY` is commented out in `.env` — which is what disarms the `_limits_ok` bypass that reported Gemini as unconditionally available. Code kept, no active path leads here
- **`codex.py`** — `codex exec` + `-c approval_policy=never` + `--sandbox read-only|workspace-write` (CLI ≥0.130; `--full-auto` deprecated) + `--skip-git-repo-check`, `--model <id>` forced; byte-only Liveness (`CLI_IDLE_TIMEOUT_NO_LIVENESS_SEC`)
- **`openrouter.py`** — HTTP/urllib (no `requests` dep), pay-per-token, NEVER in fallback chain, opt-in via `#openrouter`/`#or_*` tags, conditional registration on `OPENROUTER_API_KEY`
- **`vibe.py`** — Mistral Vibe CLI, zweite Nicht-Claude-Stimme neben Codex. Pay-per-token, NEVER in fallback chain, opt-in via `#vibe`/`#vibe_*` oder `#second_opinion:vibe`; Registrierung nur wenn das `vibe`-Binary auf dem PATH liegt. **Reviewer, kein Executor:** `read_only` → `--disabled-tools "*"`, sonst nur `read_file`+`grep` — nie `bash`/`edit`/`write_file`. `-p` **ohne Wert** = Prompt über stdin (als argv würde ein 100-KB-Prompt die Windows-Kommandozeile sprengen); `--trust` sonst Hänger am Trust-Prompt; **kein `--model`-Flag** — Modellwahl über `VIBE_ACTIVE_MODEL` (vibe-*Alias*, unbekannter Wert fällt still zurück); `PYTHONUTF8=1` im Child gegen den cp1252-`charmap`-Crash. Liefert **keine** Token-Zahlen → `RunResult` bleibt bei 0, die Schätzung im Orchestrator greift (wie Codex)
- **`opencode.py`** — opencode CLI, vierte Nicht-Claude-Stimme (Stufe 2, tag-aktiviert, `_NO_FALLBACK_PROVIDERS`-Mitglied, NICHT in `_PRIORITY` — Stufe 3 blockiert durch eine ungeklärte Hängerursache). Registrierung nur wenn `opencode.exe` auflösbar ist (nie der `.CMD`/`.ps1`-npm-Shim — `subprocess` startet eine `.cmd` nur über `shell=True`, dort bricht ein Anführungszeichen im Prompt aus der Quotierung aus) UND beide Agenten `extern-review`/`extern-dev` in `opencode.json` konfiguriert sind. Prompt geht über eine `-f`-Temp-Datei, nie stdin (entfernt den `stdin_incomplete`-Vertrag strukturell — kein Pipe-Tail zum Verlieren), gedeckelt auf `OPENCODE_MAX_PROMPT_BYTES` (50 000, in **beiden** Modi) mit hartem `prompt_too_large`-Fehler statt stiller Kürzung — begründet, weil eine Datei außerhalb `--dir` von keinem Agenten nachgeladen werden kann (`external_directory: deny` ist die LETZTE greifende Permission-Regel, gemessen 2026-09-04). Modellauflösung: `#opencode_<alias>` > optionaler externer Picker (`OPENCODE_MODEL_PICKER`, 90s Timeout, Absenz ist der Normalfall) > `OPENCODE_DEFAULT_MODEL`. Fehlerklassifikation per Keyword-Scan auf ANSI-gestripptem Text (`exit 1` ist mehrdeutig): `data policy`/`zero data retention` → `policy_block` (NICHT transient) und Rate-Limit-/402-Keywords → `rate_limit` lesen stdout+stderr, **`auth_error` liest ausschliesslich stderr** (gemessen 2026-09-04: stdout traegt nur die Antwort des Agenten, stderr nur opencodes eigenes Protokoll). Grund fuer die Asymmetrie: `unauthorized`/`forbidden`/`HTTP 403` sind die haeufigsten Woerter eines Security-Reviews, und `auth_error` kauft nachweislich **nur ein Etikett** — kein Konsument ausserhalb von `taxonomy.py` liest den Code, und ein unklassifizierter Fehler landet ueber `error_code_of() == ""` im selben nicht-transienten Ausgang. Was ein Fehlalarm real kostet, ist nicht der Task, sondern der zweite bezahlte Lauf: `orchestrator.py:1187` steigt nur fuer `TRANSIENT_ERRORS` sofort aus, jede nicht-transiente Einordnung faehrt die vollen `MAX_RETRIES_PER_PROVIDER` (2). `rate_limit` ist damit die BILLIGERE Richtung (1 Lauf) — deshalb dort grosszuegig, hier streng. Liefert **keine** Token-Zahlen (`cost=0` in 142/142 gemessen) → Schätzung greift wie bei Codex/Vibe. `openrouter_budget.fetch_budget()` (eigenes Modul, siehe unten) ist die Budgetquelle für `limits.py` — der Provider selbst ruft sie nie **Geteilter Deckel, bewusst nicht getrennt:** `OPENROUTER_API_KEY` speist den HTTP-Provider (`#openrouter`/`#or_*`) UND opencode — gemessen 2026-09-04 ist `auth.json.openrouter.key` derselbe Key. Beide zehren damit am selben $5-Tagesbudget, und ein `#or_*`-Lauf kann opencode sperren, ohne dass opencode gelaufen ist. Kein Geldrisiko (der Deckel sitzt am Key, nicht bei uns), aber eine Kopplung, die niemand erwartet — deshalb hier benannt statt stillschweigend. Trennen hiesse zwei gedeckelte Keys anzulegen und opencodes `auth.json` auf den zweiten zu zeigen; das ist eine Maschinen-Entscheidung, keine Repo-Aenderung.
- **`openrouter_budget.py`** — Live-Budget-Snapshot für den OpenRouter-Key hinter opencode, via `GET /api/v1/key` (stdlib `urllib`). Eigenes Modul statt Teil von `opencode.py`: `limits.py` importiert sonst nichts aus `providers/`, und der $/Tag-Deckel ist eine Eigenschaft des **Keys**, nicht der opencode-CLI. `fetch_budget()` kollabiert JEDEN Fehlerfall (kein Key, Netzfehler, non-2xx, kaputtes JSON, `limit_remaining: null`) zu `(None, None, None)` und wirft nie — der Aufrufer (`limits._apply_opencode_budget_override()`) ist fail-closed
- **Liveness-Watchdog statt Wall-Clock-Deadline** (`providers/process_runner.py`) — Popen + 2 Reader-Threads + Tree-Kill; idle_timeout (Hang) vs hard_timeout (Backstop). Claude tool-aware (laufender `tool_use` pausiert idle-Timer wegen stiller Tool-Phasen), Gemini/Codex byte-only mit konservativem idle. `#timeout:`/`timeout_minutes` = hard-Backstop + oberer Tool-Cap (nicht mehr aggressive Deadline). idle-Kill → `error="hang"` → Requeue mit Backoff bis `MAX_HANG_RETRIES`, dann Block (kein Quota-Reset-Retry)
- **`RunResult.error` ist ein freier String, kein Taxonomie-Code** — Provider legen dort stabile Codes ab (`rate_limit`, `hang`, …), aber ebenso rohes stderr, Exception-Text und die Form `"code: detail"` (OpenRouter `"rate_limit: …"`, Gemini `"http_429: …"`). Tools klassifizieren ihn deshalb über `providers.base.error_code_of()` / `is_transient()` statt ihn durchzureichen: ein durchgereichter stderr-Dump landete als `error_code` im generischen 5-Minuten-Cooldown statt in der passenden Behandlung, und ein hart gesetztes `retryable=True` ließ nicht-transiente Fehler über alle Provider rotieren und danach unbegrenzt requeuen. Umgestellt sind **alle 9** Tools, die Provider-Fehler in ein `ToolResult` übersetzen: `dev_loop`, `review_loop`, `test_loop`, `research_qa`, `critical_review`, `security_audit`, `deep_security_audit` und — nachgezogen 2026-08-15 — `knowledge_transfer` und `brainstorm` (gemessen per Grep auf `error_code_of`/`is_transient`). `critical_review` hatte zusätzlich eine Inline-Liste mit exaktem Stringvergleich, der `"hang"` fehlte und die die `"code: detail"`-Form nie traf. Die beiden Nachzügler waren jeweils ein eigenes Muster: `knowledge_transfer.py` (3 Stellen, Phase 1/2/3) setzte bei **jedem** Provider-Fehler `retryable=True` ohne `error_code` — ein `auth_error` oder ein Model-Refusal requeute den Task damit bei jedem Poll unbegrenzt; und `brainstorm.py` (Synthesis-Zweig) schob den rohen `RunResult.error`-String als `error_code` durch und prüfte Transienz per Exakt-Vergleich gegen `("stdin_incomplete",)` — was `rate_limit`/`unreachable`/`timeout` als permanent abstempelte und die reale `"stdin_incomplete: 3 of 12 KB"`-Form gerade **nicht** traf. `brainstorm` behält seinen Tool-Code `synthesis_failed` als Fallback, wenn `error_code_of()` bei Freitext-stderr leer zurückkommt
- **`orchestrator.py` selbst konnte `error_code` mit Rohtext füllen — Fix + neuer Code `auth_expired` (2026-09-16).** Die Tool-Normalisierung oben (`error_code_of()`/`is_transient()`) deckt nur ab, was ein Tool an `orchestrator.py` meldet; die eigenen Schreibstellen nach `runs.jsonl` hatten dieselbe Lücke ein Stockwerk höher. Drei Stellen schrieben einen unklassifizierten Fallback direkt in `_span`: `error or "rate_limit"` im Single-Shot-Pfad (`provider_is_forced`-Zweig), `outcome.error_code or "rate_limit"` im analogen Tool-Pfad, und `tool_result.error_code or tool_result.error` in `_execute_tool_task()`. Gemessen in `logs/runs.jsonl`: am 2026-09-09 landeten genau drei Rohtexte als `error_code`, darunter wörtlich `"Failed to authenticate: OAuth session expired and could not be refreshed"` — ein Claude-CLI-OAuth-Ablauf, den `providers/claude.py` bis dahin gar nicht erkannte (anders als Gemini/OpenRouter/opencode/Vibe, die HTTP-401/403 längst auf `auth_error` mappen). Alle drei Stellen normalisieren jetzt über `error_code_of()` mit einem taxonomie-bekannten Fallback (`provider_unreachable`/`tool_internal_error` statt dem sachlich falschen `rate_limit`), und `providers/claude.py` klassifiziert den exakten, eng gewählten Wortlaut `"oauth session expired"` (bewusst NICHT die breiten `heartbeat._PROBE_TRANSIENT_KEYWORDS` — die wären in normaler Coding-Prosa über OAuth-Handling falsch-positiv) als eigenen Code `auth_expired`. Bewusst NICHT in `TRANSIENT_ERRORS`: nur ein manuelles `claude login` behebt es, automatisches Warten nicht — anders als `rate_limit`/`timeout`/`hang`/`stdin_incomplete`. Behandlung auf den beiden `run_once()`-Pfaden (Single-Shot, Tool-Task): dieselbe Cooldown-Mechanik wie `unreachable` (`provider.set_cooldown()`, Standard 30 min, keine neue Zahl) plus ein einmaliger Telegram-Hinweis pro Ausfall (`orchestrator._notify_auth_expired_once()`/`_clear_auth_expired_notice()`, Dedup-Technik wie `limits._429_notified`/`_clear_429_state` — eigene Instanz, weil 429- und Auth-Zustand unabhängig sind). Taxonomie-seitig teilt sich `auth_expired` die Kategorie `CAT_AUTH` mit `auth_error` statt eine eigene zu bekommen — deren Definition ("credentials missing / expired") passt exakt.
  - **Runde 2 (2026-09-16): `_run_with_retry()` verlässt die eigene In-Run-Backoff-Schleife jetzt auch für `auth_expired`** — eigener Bare-Code-Check, NICHT durch Aufnahme in `TRANSIENT_ERRORS` (das würde `is_transient()` umdefinieren und Konsumenten treffen, die sich darauf verlassen). Ohne den Check verbrannte die Schleife 10-40 s auf einen zweiten, garantiert ebenso scheiternden CLI-Aufruf gegen dieselbe Session. `auth_error` bleibt unverändert (eigener Test).
  - **`#parallel`-Subtasks bekommen den Hinweis, aber KEINEN Cooldown, und der `#parallel`-Elterntask retryt/parkt bei KEINEM Fehlercode (benannte Grenze, nicht gebaut).** `parallel_runner._run_single_subtask()` ruft jetzt `_notify_auth_expired_once()` auf (dieselbe Dedup-Hilfsfunktion, keine zweite Mechanik), setzt aber keinen Cooldown — das ist keine neue Lücke, sondern eine bestehende: der parallele Pfad kennt heute für KEINEN Fehlercode (`rate_limit`, `unreachable` eingeschlossen) einen Cooldown. Das zu schließen bräuchte eine Entscheidung, wie ein aus einem parallelen Worker-Thread gesetzter Cooldown mit Geschwister-Threads am selben Provider-Singleton interagiert — außerhalb dieses Scopes, benannt statt stillschweigend umgangen.
  - **Runde 3 (2026-09-16), P1: derselbe Finalisierungs-Fallstrick geprüft für den `#parallel`-Pfad — nicht vorhanden, weil dort schon vorher unconditional finalisiert wird.** `run_once()`s `#parallel`-Zweig finalisiert die Elternzeile IMMER sofort nach `run_parallel()` (`_finalize_task_with_result_checked(..., failed=not success_all)`), egal welcher Fehlercode eine Subtask scheitern ließ — kein Retry, kein Park, für JEDEN Code, nicht nur `auth_expired` (Design-Entscheidung #7: „the parent gets one aggregated result"). Der P1-Fix unten wirkt hier nicht: `_run_single_subtask()` liest `outcome.finalized`/`.retryable` nie, nur `.success`/`.error_code`/`.output` — die Überschreibung ist für den parallelen Pfad unsichtbar, in beide Richtungen. Nicht gebaut (siehe ROADMAP.md): eine Entscheidung, ob/wie ein `#parallel`-Elterntask je pro Subtask statt als Einheit re-parkt werden könnte.
  - **Runde 3 (2026-09-16), P1: `is_transient("auth_expired") == False` machte den ganzen Fix wirkungslos für Tool-Tasks.** Die sieben mehrphasigen Tools (`dev_loop`, `review_loop`, `research_qa`, `knowledge_transfer`, `security_audit`, `test_loop`, `brainstorm`) setzen `retryable=is_transient(error)` generisch für JEDEN Provider-Fehler in ihren Phasen — für `auth_expired` also `retryable=False`. `_execute_tool_task()` nahm dadurch den nicht-retryable-Zweig und finalisierte den Task SOFORT mit `failed=True` (`_finalize_task_with_result_checked(..., failed=True)`), bevor der `auth_expired`-Cooldown/Notify-Zweig der äußeren Schleife je erreicht wurde — reproduziert vom Reviewer: `outcome.finalized=True`, kein Cooldown, kein Hinweis, Task endgültig gescheitert, exakt entgegen der ANNAHME. Fix: in `_execute_tool_task()` (Zeile ~1943 ff.) wird `tool_result.retryable or _tr_error_code == "auth_expired"` geprüft statt nur `tool_result.retryable` — dieselbe „Code vor der Finalisierungs-Entscheidung abfangen"-Form wie bei `capacity_exhausted`/`tool_runtime_exceeded`, nur dass jene zwei Codes bereits TOOL-seitig hart `retryable=True` bekommen (`_make_capacity_exhausted_result`, `dev_loop._terminal_runtime`), während `auth_expired` generisch durch `is_transient()` läuft und deshalb hier, an einer zentralen Stelle, statt in allen sieben Tools abgefangen wird. `tests/test_orchestrator_tool_tasks.py::test_run_once_tool_task_auth_expired_sets_cooldown_and_notifies_once` (P2) mockte vorher `ToolTaskExecutionOutcome` direkt und hätte diese Regression nie gesehen — umgebaut auf ein Fake-Tool, dessen `run()` `retryable=is_transient(error_code_of(error))` liefert, exakt wie ein echtes Tool; Mutationsbeweis: ohne den P1-Fix bricht die Rotation nach dem ersten (permanent gescheiterten) Versuch ab, `tool.run.call_count == 1` statt `2`.
  - **Runde 4 (2026-09-16), letzte Runde an diesem Mechanismus: `auth_expired` überlebt nicht in jedem Tool als Kopf-Code.** `tools/scientific_investigation_phases.py` wirft bei jedem Provider-Fehler `RuntimeError(f"... failed: {result.error}")`; `tools/scientific_investigation.py` macht daraus `error_code="phaseN_failed", retryable=False` — der ursprüngliche `auth_expired`-Code überlebt nur noch als Text INNERHALB der gewrappten Meldung, nie als extrahierbarer Kopf. Zentraler statt Tool-seitiger Fix: `providers.base.contains_auth_expired()` (wortgrenzen-sicherer Token-Scan, `(?<![\w-])auth_expired(?![\w-])`) sucht in `_execute_tool_task()` direkt im `tool_result.error`-Text und überschreibt `_tr_error_code` auf `"auth_expired"`, bevor die Retryable-Entscheidung fällt — eine Klassifikationsquelle, keine zweite. Damit ist der Fix für JEDES aktuelle und künftige Tool geschlossen, das Provider-Fehler generisch in eigenen Text verpackt. Andere Codes (`rate_limit` usw.) bleiben in solchen Tools verloren — vorbestehend, in ROADMAP.md benannt, nicht gebaut (das Tool läuft über die Queue faktisch nicht). Mutationsbeweis: die Token-Scan-Zeile entfernt → der Hauptfall wird rot, die beiden Gegenproben (`auth_expired_foo`, `not_auth_expired`) bleiben unverändert grün. **Fixed 2026-09-17:** the "andere Codes bleiben verloren" gap above is closed — `providers/base.py` gained `ProviderCallError(RuntimeError)` carrying the raw `RunResult.error` structurally, all 7 provider-failure raise sites across `scientific_investigation_phases.py`/`_phase2.py`/`_phase4.py`/`_phase5.py`/`_phase7.py` raise it instead of a bare `RuntimeError`, and `scientific_investigation.py` catches it before the generic `except (RuntimeError, ValueError)` in all 5 affected blocks, classifying via `error_code_of()`/`is_transient()` — see ROADMAP.md's closed-defects list.
