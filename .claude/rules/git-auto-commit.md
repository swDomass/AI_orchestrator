# Git Auto-Commit (git_commit.py)

Ausgelagert aus CLAUDE.md am 2026-09-21; laedt automatisch bei Zugriff auf git_commit.py.

- **`git_commit.py`** — Per-Task-Auto-Commit (2026-09-10): `commit_run_result()` legt die Arbeit eines erfolgreichen Laufs auf `orch/<slug>-<datum>` ab und setzt danach genau diese Pfade im Arbeitsbaum auf HEAD-Stand zurück. **HEAD wird nie bewegt** — Commit über temporären Index (`GIT_INDEX_FILE`) + `commit-tree` + `update-ref`, Vorbild ist `orchestrator._git_snapshot`. Aufgerufen aus `orchestrator._commit_run_changes()` an beiden Erfolgspfaden, hinter `if verify.ok:`. Details unten unter Key Patterns
- **Der Orchestrator committet selbst — ein Branch pro Task (2026-09-10)** — Gegenstück zum Arbeitsbaum-Gate darunter: das Gate *verhindert*, dass ein schmutziger Baum einen dev-loop verfälscht, dieses Feature sorgt dafür, dass gar nicht erst einer entsteht. Nach einem erfolgreichen Lauf legt `git_commit.commit_run_result()` genau die Pfade des Laufs auf `orch/<slug>-<YYYY-MM-DD>` ab (`slug` = `#id:` falls vorhanden, sonst `sha256(strip_metadata_tags(task))[:8]`, git-ref-sanitisiert) und setzt sie danach im Arbeitsbaum auf HEAD zurück. Morgens steht damit pro Task ein Branch zum Lesen/Mergen/Wegwerfen, und der ZWEITE `#tool:dev-loop` im selben Repo stirbt nicht mehr an `worktree_dirty`. Default an, global über `GIT_AUTO_COMMIT=false` in der `.env` aus, pro Zeile über `#no-commit`.
  - **HEAD wird nie bewegt — Plumbing statt Checkout-Tanz.** Temporärer Index (`GIT_INDEX_FILE`) + `commit-tree` + `update-ref` (leerer oldvalue = create-only, `_2`-Suffix bei Kollision), also dasselbe Muster wie `_git_snapshot`/`_prune_snapshot_refs`, das der Auftrag als Vorbild vorschreibt. Ein `git checkout -b` / `git checkout <orig>`-Paar wäre kürzer, hinterlässt aber bei einem Absturz zwischen den beiden Kommandos HEAD auf einem fremden Branch — **exakt der gemessene `nightstash`-Fehler vom 03.09.**, den das Feature beheben soll. Beim Plumbing-Weg ist der schlimmste Absturzzustand „Branch existiert, Baum noch schmutzig" = der Status quo, nie schlechter. `read-tree` und `checkout` nehmen den **einmal erfassten `head_sha`**, nicht das symbolische `HEAD`: sonst beschriebe der Baum einen anderen Ausgangspunkt als der Elternteil, sobald HEAD dazwischen wandert, und fremde Commits sähen im Branch aus wie unsere.
  - **ZWEI Regeln tragen die Sicherheitszusage, eine allein reicht nicht.** Regel 1 ist die Index-Regel unten. Regel 2 (`dirty_before`, vom Orchestrator neben `snap_before` **vor** dem Lauf aufgenommen): ein Pfad wird nur angefasst, wenn er beim Start des Laufs **sauber** war. Grund, im adversarialen Review am echten Repo gemessen und nicht hergeleitet: die ganze Zuordnung „was hat der Lauf geändert" ist ein `(mtime, size)`-Vergleich, und dessen Fenster ist die **gesamte Laufzeit** — Minuten bis Stunden bei einem dev-loop, während `--watch` durchläuft und der User an derselben Maschine sitzt. Jede Handbearbeitung in diesem Fenster las sich als Arbeit des Laufs: committet unter unserer Message **und im Arbeitsbaum auf HEAD zurückgesetzt**, mit `git status` danach auf „sauber". Die Index-Regel fängt das nicht — sie fragt, ob etwas **gestaged** ist, nicht wer es geschrieben hat, und niemand staged mitten im Tippen. `dirty_before is None` heißt „Baseline nicht ermittelbar" und ist ausdrücklich **nicht** dasselbe wie „nichts war schmutzig": dann wird gar nicht committet, weil die Zuordnung unbelegbar wäre. Kostet nichts, wo das Feature wirklich benutzt wird — `requires_clean_worktree` garantiert für jeden `#tool:dev-loop` eine leere Baseline —, und greift nur beim Single-Shot in einem ohnehin schmutzigen Baum, also genau dort, wofür es existiert.
  - **Der Deckel `GIT_COMMIT_MAX_FILES` zählt die committbaren Pfade, nicht die rohe Snapshot-Differenz — und stand vorher an der falschen Stelle.** Vor dem git-Sichtbarkeitsfilter zählte er jede gitignorierte Datei mit, die der Lauf nebenbei angefasst hat. In genau diesem Repo gemessen: **5011 gitignorierte Dateien, 496 davon in 24 h verändert, 61 in der letzten Stunde** (`__pycache__`, `.ruff_cache`, `.mypy_cache`, `logs/`, `.dev-loop/`) — ein 3-h-dev-loop, der wie oben vorgeschrieben pytest + ruff + mypy als letzten Schritt fährt, hätte 200 regelmäßig gerissen. Der Ausfall wäre **still** gewesen: Task grün, Baum schmutzig, Ursache erst sichtbar, wenn der nächste dev-loop an `worktree_dirty` stirbt — also am ursprünglichen Bug. Das Feature hätte sich in dem Repo, für das es gebaut wurde, selbst abgeschaltet. Aus dem adversarialen Review, dort mit eigener Messung belegt (206 Kandidaten, davon 1 git-sichtbar).
  - **Die tragende Invariante: angefasst wird nur, wo der Index mit HEAD übereinstimmt.** Ein Pfad kommt nur in den Commit (und nur ins Cleanup), wenn seine porcelain-Index-Spalte X `' '` oder `'?'` ist — `_TOUCHABLE_INDEX_X`, bewusst eine **Erlaubnis-, keine Verbotsliste** (ein künftiges neues Statuszeichen wird dann übersprungen statt committet). Gemessen, warum: `git checkout HEAD -- <pfad>` auf einem Pfad mit fremd gestagtem Inhalt vernichtet diesen aus Index **und** Arbeitsbaum, und in unseren Commit kommt er auch nicht (`git add` nimmt den Arbeitsbaum-Stand). Die Regel schließt damit strukturell drei Fälle auf einmal: fremdes Staging (`MM`/`AM`), **Merge-/Rebase-Konflikte** (`UU` — ein laufender Merge bleibt vollständig intakt, ohne dass es dafür Sonderbehandlung gäbe) und Renames (zusätzlich wird `R`/`C` in *beiden* Spalten ausgeschlossen, sonst stünde im Branch der alte UND der neue Name). Übersprungene Pfade gehen als WARNING auf `print` **und** `logger` und ihre Zahl als `CommitOutcome.skipped_paths` in die Telegram-Meldung — ein Commit kann erfolgreich UND unvollständig sein.
  - **`:(literal)` ist nicht optional.** `--` beendet nur das Optionsparsing, es literalisiert keine Pathspecs — git liest sie als Glob. Gemessen: mit einer Datei `config[.]py` im Baum stagt `git add -A -- 'config[.]py'` **zusätzlich die fremde `config.py`**, deren X-Spalte nie geprüft wurde; das Cleanup hätte sie danach auf HEAD zurückgesetzt. Genau die Datenverlust-Klasse, die die Index-Regel ausschließt, an ihr vorbei. Extern gefunden (Codex), reproduziert, gefixt, per Test festgenagelt.
  - **Zwei Pfad-Räume, eine Brücke.** `git status --porcelain` liefert Pfade relativ zum **Worktree-Root**, `_snapshot_dir` relativ zum **`cwd` des Tasks**. Bei einem `cwd:` unterhalb des Repo-Roots war die Schnittmenge deshalb immer leer und das Feature dort still tot; `git rev-parse --show-prefix` überbrückt die Differenz (am Root leer, also unverändertes Verhalten). `-z` ist ebenfalls tragend: ohne es quotet git Pfade mit Nicht-ASCII oktal (`"Pr\303\274fbericht"`) und **jede Datei mit Umlaut fiele still aus der Menge** — auf einem deutschen Windows-Rechner kein Randfall.
  - **Die eigenen Buchhaltungsdateien sind nie Task-Arbeit.** Queue-Datei, ihr `.lock` und `agent-queue-erledigt.md` werden aus der Commit-Menge geworfen (aus `queue_manager.QUEUE_FILE` **abgeleitet**, nicht hand-kopiert). Grund: `finalize_task_with_result` schreibt den ✅-Stempel VOR dem Commit (Reihenfolge ist GUARDRAIL), er steckt also in `snap_after` — mitcommittet und danach auf HEAD zurückgesetzt wäre die Finalisierung im Arbeitsbaum rückgängig, die Zeile wieder offen, der Task liefe bei jedem Poll erneut. Heute nicht erreichbar (der Vault ist kein Git-Repo, gemessen 2026-09-10), aber **fünf Queue-Tasks tragen ein `cwd:` auf den Vault** — ein `git init` dort würde reichen. Extern gefunden (Codex).
  - **Kopplung an `#verify:` und die Reihenfolge.** Der Aufruf hängt in **beiden** Erfolgspfaden (`_execute_tool_task`, `run_once`) im Zweig `if verify.ok:`, also NACH Finalisierung und NACH dem Ergebnis-Check — beide Richtungen tragen: ein Verify-Skript inspiziert Artefakte im Baum, die nach dem Commit dort weg sind; und ein rotes `#verify:` heißt „Lauf meldete Erfolg, hat aber nichts geliefert" und darf nicht committet werden. Ohne `#verify:`-Tag ist `VerifyOutcome().ok` True, der eine Zweig deckt also „kein Tag" und „Tag grün". `#parallel`-Subtasks committen strukturell nicht (`skip_queue=True` überspringt den ganzen Block), read-only-Tools ebenfalls nicht (dieselbe Bedingung, die schon `_git_snapshot` steuert).
  - **Ein Fehlschlag beim Committen macht den Task nicht rot.** `commit_run_result` wirft nie (äußeres `except BaseException`) — **außer `KeyboardInterrupt`/`SystemExit`, die davor re-raised werden**, sonst schluckte ein Commit-Versuch das `SystemExit` der Shutdown-State-Machine und ein geordnetes Herunterfahren hinge davon ab, ob es zufällig währenddessen ausgelöst wurde (dieselbe Reihenfolge-Regel wie in `main()`). `_commit_run_changes` fängt zusätzlich ab, weil das `_snapshot_dir(cwd)` in der Argumentliste außerhalb des Modul-Handlers läuft und eine Exception dort `run_once` verlassen würde (der `#tool:`-Zweig ist nur in `try/finally` gewickelt) — der Task bekäme einen erfolglosen Versuch auf dem Absturz-Zähler, den er nicht verdient hat.
  - **Wechselwirkung mit `#needs:`-Ketten — die praktisch wichtigste Grenze.** Eine Kette, deren spätere Schritte den **uncommitteten** Diff der früheren prüfen, bricht ohne `#no-commit`: Schritt 1 committet und räumt den Baum, Schritt 2 prüft nichts. Genau so stand die im README empfohlene 8-Schritt-Vorlage da (gefunden im Doku-Sweep 2026-09-11, nicht beim Bau) — sie trug die Prosa „dont commit the changes!", und die richtet sich an den *Provider*; der Commit des Orchestrators liest keine Prosa, nur den Tag. Vorlage korrigiert: `#no-commit` an allen schreibenden Schritten außer dem letzten, `critical-review` braucht es nicht (`read_only=True`, gemessen). Wer eine eigene Kette baut, muss dasselbe tun.
  - **Benannte Grenzen, nicht entdeckt sondern benannt:** Das Zeitfenster zwischen Statusaufnahme und `git add` bleibt offen (eine fremde Änderung an *unseren* Pfaden würde mitcommittet — falsch zugeordnet, aber im Branch erhalten); die *zerstörende* Hälfte ist geschlossen, weil direkt vor dem Cleanup ein zweiter `git status` läuft und veränderte Pfade unangetastet lässt. Tool-Artefaktverzeichnisse (`.dev-loop/`) landen mit im Commit, wenn das Zielrepo sie nicht gitignoriert. `_snapshot_dir` vergleicht `(mtime, size)`, inhaltsgleiche Rückschreibungen und reine Mode-Änderungen fehlen also (sichere Richtung: bleiben uncommittet). Windows-Gerätenamen (`nul`) lassen sich nicht per `os.remove` löschen → `worktree_cleanup_failed` als lautes WARNING statt einer Filterliste, die mit Windows driften kann. **Zeilenenden:** das Cleanup läuft über `git checkout`, also durch die Filter von git selbst — in einem Repo **ohne** `eol=`-Attribut und mit `core.autocrlf=true` (auf dieser Maschine system-weit gesetzt, nachgemessen mit `git config --system`) kommt eine Datei mit vormals LF-Enden als CRLF zurück, byte-verschieden vom Ausgangszustand. Bewusst nicht umgangen: es ist exakt das Verhalten jedes `git checkout` in so einem Repo, `git status` bleibt danach sauber, der committete Blob trägt ohnehin den normalisierten Inhalt, und an den Filtern vorbeizuschreiben wäre schlimmer als der Effekt. AI_orchestrator selbst ist nicht betroffen, weil seine `.gitattributes` `* text=auto eol=lf` setzt und `eol=` das `core.autocrlf` überstimmt. Stirbt der Prozess zwischen Finalisierung und `update-ref`, ist der Task grün ohne Branch — die Arbeit liegt dann unangetastet im Baum. Retention für alte `orch/*`-Branches, `#parallel`/`#worktree`, Push/PR/Merge und modellgenerierte Commit-Messages sind KÜR und **nicht** gebaut.
  - **Der Cleanup-Guard vergleicht INHALT, nicht nur den Statuscode — und ist fail-closed.** Zwischen der ersten Statusaufnahme und dem Aufräumen liegen mehrere Git-Aufrufe. Zwei verschiedene fremde Zugriffe müssen dort abgefangen werden, und sie brauchen zwei verschiedene Prüfungen: **gestaged** (XY ändert sich, `checkout` würde den Index-Stand mitreißen) und **weiter geschrieben** (XY bleibt auf ` M`, während sich die Bytes ändern). Die erste Fassung prüfte nur XY und hätte den zweiten Fall gelöscht — also genau die Datenverlust-Klasse, die dieser Guard schließen sollte. Der Test dazu war in derselben Fassung wertlos: er stellte den Statuscode um und prüfte damit den Fall, den der Code ohnehin abdeckte, statt den, den die Behauptung verspricht. Beides extern gefunden (Grok). Jetzt zusätzlich `(mtime, size)` gegen den bei `snap_after` aufgezeichneten Stand, und eine **fehlgeschlagene** zweite Aufnahme überspringt das Cleanup vollständig statt über alle Pfade zu laufen (fail-closed; vorher fail-open genau in dem Moment, in dem unbekannt ist, ob die Pfade noch die gemessenen sind). Geerbte Grenze: eine Inhaltsänderung mit identischer mtime UND Größe bleibt unsichtbar.
  - **Ein `skipped` ist nicht immer harmlos.** Die meisten Gründe sind es („kein Repo", „kein Diff", „abgeschaltet") und bleiben still. Zwei nicht: `too_many_files` und `nothing_git_visible` **mit** `skipped_paths > 0` bedeuten „es GAB Arbeit, sie liegt uncommittet im Baum" — und genau daran stirbt der nächste `#tool:dev-loop` im selben Repo. Beide gehen jetzt in die Telegram-Meldung, statt nur auf `print`/`logger`. Ebenfalls extern gefunden.
  - **Der Cleanup-Timeout ist eigens hochgesetzt (`GIT_COMMIT_CLEANUP_TIMEOUT_SEC`, 120 s statt der sonstigen 30 s), weil dort das REPO auf dem Spiel steht und nicht nur der Commit:** ein gekilltes `git checkout` kann `.git/index.lock` zurücklassen, und danach scheitert **jeder** git-Aufruf in diesem Repo — unbeaufsichtigt, und der Watchdog hilft nicht, weil die Sperre eine Datei ist und kein Prozess. Ein Checkout auf einem OneDrive-Repo muss Platzhalter rehydrieren und einen Virenscanner passieren. Die Sperre wird bewusst **nicht** automatisch gelöscht (sie kann einem fremden, lebenden git gehören); stattdessen eine eigene `TimeoutExpired`-Meldung, die `.git/index.lock` beim Namen nennt. Mechanismus extern gemeldet (Grok), nicht reproduziert.
  - **`_orchestrator_state_paths()` vergleicht über `realpath`, nicht `abspath`** — ein `subst`-Laufwerk, eine Junction oder ein 8.3-Kurzname zeigen auf dieselbe Datei unter anderem Namen, und ein reiner Textvergleich hätte den Schutz genau dort verfehlt, wo er gebraucht wird. Der Archivname wird aus `queue_manager._ERLEDIGT_FILE` abgeleitet statt als Literal geführt.
  - **Review-Bilanz (Stufe 2):** Mistral P1 keine / 3 P2, Codex 4 P1 + 11 P2, opencode P1 keine / 3 P2, Grok (opencode `zdr-auto-1`) 2 P1 + 4 P2 + 1 P3, interner Devil's Advocate (Opus) 2 P1 + 5 P2 + 5 P3 — die letzten beiden Runden liefen gegen den jeweils schon korrigierten Stand. Davon gebaut: **20 Befunde**. **Die zwei teuersten kamen aus der LETZTEN Runde**, und beide widerlegten eine Behauptung, die schon in der Doku stand: die Index-Regel schließt nur die *gestagte* Hälfte der Datenverlust-Klasse aus (nicht „strukturell" die ganze), und der Datei-Deckel hätte das Feature in diesem Repo still abgeschaltet. Lehre für die nächste Stufe-2-Runde: **einen Reviewer auf den bereits korrigierten Stand ansetzen, mit einer Ausschlussliste des schon Gefundenen** — er sucht dann die Lücken IN den Fixes statt die, die alle finden. Beide letzten Runden haben so etwas gefunden, die ersten beiden nicht. Widerlegt statt übernommen: Codex' „der temporäre Index bricht jeden Commit ab" (die Tests gegen echte Repos laufen grün) und der `MM`-Fall, den Codex als unwiederbringlichen Verlust beschrieb (der Inhalt steckt im Branch). Die interne Multi-Agent-Runde starb zunächst am Claude-Session-Limit; opencode und Grok haben als externe Stimmen übernommen. **Lehre aus Groks Runde:** ein Reviewer, der den bereits korrigierten Stand UND eine Ausschlussliste des schon Gefundenen bekommt, findet die Lücken IN den Fixes — die teuersten zwei Befunde des ganzen Pakets kamen erst aus dieser vierten Runde.
